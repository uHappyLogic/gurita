## Purpose

For maintainers of `core/agents/`: the two dispatched subagents, `complete-task`, dispatched once per task by `complete-all-tasks`, and `provide-alternatives-to-open-question`, dispatched once per bare question block by the alternatives pass. Each agent reads only its own file (the completion agent also the procedure it follows), and that text is its exact behaviour. This node holds the rules an edit must keep for an agent, its dispatch prompt, and its return contract, with reasons and retired forms. No host renders it: every `scripts/hosts/<host>/settings.toml` excludes it.

## Rules

- **A dispatch prompt carries only what the orchestrator already holds and the agent cannot fetch itself.** `complete-all-tasks` passes the task's `##` heading text, the alternatives orchestrator the question's Short Title, and each the resolved `<MISSION_DIR>` and the run's scratch directory, nothing else; the agent fetches the rest under the mission directory (its task section; its block by `locate` and its sibling scope by `list --with-question`; `requirements.md`). Both prompt fences carry one fixed `Mission directory: <MISSION_DIR>` line and one fixed `Scratch directory: <scratch dir>` line on every dispatch, on every host, unconditionally, the same directory for every agent of a run, and the agent uses both as given, resolving nothing. The body file added no line: it lands under its own fixed name beside `paths.txt`, and the bar travels in no message either way, the orchestrator passing none and receiving none. The rule constrains the prompt, not what an agent reads whole, which is fixed per document. Reason: the orchestrator holds no work context, so an extra slot is something it gathers and holds per dispatch only to hand over, a fetchable value is delivered twice (under the old prompt the alternatives agent read its block in the prompt and again in its whole read of `open_questions.xml`), and a fetch gives the live document, not a snapshot. The two directories pass because the agent cannot fetch them: the `--mission` value reaches it no other way and nothing stored says which live mission the orchestrator commits for, and each orchestrator makes its own scratch directory with `mktemp -d` once per run; one unconditional shape keeps prompts and agent files host-neutral. Retired forms: the `Question block:` slot, the orchestrator's per-question `locate` gather (the pass's two `list` calls are its whole gather), a resolution inside the agent.
- **The completion agent returns a bare token and two fixed-name files.** `complete-all-tasks` makes the run's scratch directory once with `mktemp -d` before the first dispatch. On `DONE` the agent has written its bar to `<scratch dir>/body.txt` and its whole change set (the procedure's recorded paths plus `<MISSION_DIR>/TASKS_TODO.md`, one per line, never from `git status` or any tree-wide selection) to `<scratch dir>/paths.txt`, nothing above the token. Its step-5 call opens as the inline skill's does: it captures the bar once and tests it holds a non-blank line ahead of `remove` behind `&&`, then writes the body file and the path file only after `remove` succeeds, so nothing reaches the scratch directory unless the test and the removal both pass, both runners share one bar-handling form, and the write-nothing-else contract needs no carve-out; an empty bar prints the call's one line and removes, writes, and commits nothing, and the agent fixes the bar and reruns. The orchestrator reads the last line only, then commits from the two files; its `body file absent` and `body file empty` tests stand beside its two path-file tests, each committing nothing and stopping under `Task run stopped — a completed task could not be committed.`, so no fixed line was added; once read, whatever the outcome, both files move into a `processed` subdirectory under `mktemp`-unique names. The final message is exactly one line, `DONE` or `FAILED: <reason>`, any summing up done in an earlier turn, and every command runs in the foreground within its call, no turn ending while a started process runs. A `FAILED` promises a resumable tree (partial work continued, never redone or reverted), writes neither file, and stages and commits nothing. A failed past-work read, `tasks` or `show`, whatever the reason, is never a `FAILED`: the agent carries on from `requirements.md`, the context file, and the live material and reports nothing, the procedure saying so in a clause of its own against its never-skip rule. Reason: the bar crosses a process boundary only here and must not be re-typed by an orchestrator holding no work context, so it rides as a second file the existing commit-from-file call already reads; the task list rides in the path file because the call already names it, so the orchestrator names no path; names come from no title because a heading holding `/` or `"`, both among recorded headings, would end a run with its work done and its list unwritten; moving the files costs no turn, deletes nothing, keeps every bar and list on disk, and leaves fixed names absent for the next agent, so a missing file shows. 58 of 415 field `DONE` returns since 2026-11-18 carried a summary above the token, and 15 of 1,945 agents ended on neither line, most a turn ended waiting on a background process; a return with no token still stops the run on its no-status line, the fail-safe. A read the agent may skip must not end an unattended run over a mistyped path, and a git-level fault still stops it at the scope gate or the commit. Retired forms: the untouched-tree `FAILED` promise, the staging contract and the orchestrator's whole-index commit, a bar or path list in the final message, a payload above `DONE`, a title-derived file name, deleting the files.

- **The alternatives agent returns a file, not a message.** Its one write, the sole exception to its read-only contract, is `<scratch dir>/<Short Title>.xml` in the run's directory, made once per run by `mktemp -d`, fresh and uniquely named under the system temp location so no stale return or concurrent run collides with it, in the same wording in every host tree and writable under a workspace-write sandbox. It writes under `.xml.part` and renames with one `mv` in the same directory, then ends on the bare `DONE` or `FAILED: <reason>`. The orchestrator's only judging is the last-line `FAILED:` verdict, which gets no repair; all else is one fixed batch shell call that scans exactly the `*.xml` files directly in the run directory, redirects each unedited into `embed --alternatives` (the tool slices and validates), commits each accepted question, prints one line per refused file or failed commit, and moves every piped file, accepted or refused, into `processed`, so no file is piped twice and the record of what was piped lives on disk, never in the orchestrator's context. Every refusal a batch prints gets its one repair at once, all in one turn, the branches (continue the held session, or one fresh re-dispatch once the handle is gone) and the wait written per host in the `ALTERNATIVES_REPAIR` slot; the repaired file lands at the same path for a later batch, whether a question had its repair is the only thing tracked, a second refusal or `FAILED:` skips the question, and a wait returning before every awaited agent ended waits again, without limit, so an expiry never skips one. No `DONE` is cross-checked: the closing `list --without-alternatives` catches every file that never landed and leaves its block bare. The orchestrator deletes nothing, no scratch file, `processed` subdirectory, or run directory, and its prose holds no delete or recursive-remove command; the system's temp handling reclaims the directory. Markup in an alternative's text is accepted as it stands, with no change to the agent's file, the corrective message, or the tool. The batch is scoped to this agent: `complete-all-tasks` keeps its token verdict and fixed-name files with no scan, repair, or batch. Reason: a file keeps a return from crossing the orchestrator's context twice, as a message and again in a heredoc for `embed`; the rename stops a scan piping a half-written file; the path is fixed at dispatch, so the batch takes the title from the file name and a title holding a path separator (only a pre-refusal block can) fails visibly as a `FAILED:`; a cross-check needs the per-agent list the batch keeps out of context; deleting nothing meets no permission prompt in a headless chain and keeps refused returns for inspection. The per-return pipeline cost about 16 post-dispatch turns per run over 21 measured runs, over half text-only or silent, at a median 57k-token context holding every return twice, against an estimated 0.82M input tokens per mission saved (1.17M with one outlier). Piping the whole unedited return, repairing once, then skipping reversed discard-whole, which lost eight of ten dispatches to a grounding preamble; markup is accepted because the eight refused field returns were each recovered by the one repair, whose `Error:` line names the failing position, and a refused file never reaches the document. Retired forms: the per-return pipeline, a returned path, a `DONE` cross-check, a cleanup step, discard-whole or skip-only handling, extraction in prose.
