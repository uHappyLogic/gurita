## Purpose

For maintainers of `core/shared/`: each procedure is the single source of truth for one unit of work two or more runners reference, and its text is its exact behaviour. This node holds the rules an edit must keep, with reasons and retired forms. No host renders it: every `scripts/hosts/<host>/settings.toml` excludes it.

## Rules

- **Every skill inside an existing mission resolves it through `resolve-mission.md`, from one required leading `--mission <path>`.** No mission is current: nothing stored or computed picks one, so each run names its own. The value is the path the definition tool printed, trailing slash included, verbatim (nothing added, stripped, looked up, or supplied); it matches when it ends in `/` and `<path>/requirements.md` exists in the working tree, with no `mission_` check (the gate's). A missing flag, value, or match stops on the procedure's one fixed line, the `live` print or `Error:` line beneath, with no fallback. The flag rule (first whitespace-separated token exactly `--mission`, the next its value, the rest the skill's text) is stated once here; a skill with positional text strips it by one clause at its parse point, so it never reaches the skill's own text, and every Usage fence, skill-reference heading, and per-mission chain line in `docs/` spells it. It covers the seventeen skills using an existing mission, none creating or preceding one: the completion procedure's step 1 takes a supplied directory as given, resolving only without one, `complete-all-tasks` forwarding its own; `capture-mission-principle-updates` alone keeps a positional `<path>`, found in the tree or else by a path-scoped `git log -1` on its `requirements.md`, its mission maybe finished; `ask-in-mission-context` stays tree-only. Reason: the path alone tells missions apart, the same in every skill, subject, and tool line; a fallback runs a skill on a mission nobody named; typing it is the accepted cost. Retired forms: a current mission in any form, in the tree or out of it (an environment variable, an ignored file); a normalized value; a fallback.
- **A started mission holds its scope, checked through `check-scope-gate.md` at the four task sites.** It runs `gate <MISSION_DIR>`: the scope is free exactly when it prints nothing on either stream and exits 0; anything else (a holder, a shallow clone, a path naming no `mission_` directory) is one condition, stopping the runner unchanged on the procedure's one fixed line, the holders or `Error:` line beneath. Another live mission is started once tasks were ever entered in its list and holds while its scope equals, contains, or lies under this one's, until finish removes it, done or not; a defined or deciding one holds nothing, so overlapping missions prepare freely and wait only at task entry, disjoint ones run at once, and no order comes from a number, definition time, or pointer. `derive-tasks` and `submit-task` check twice, as two steps: right after resolution, before the staleness check, reads, refresh, or authoring, and right before the write (a refresh committed before a closed second check stays; a run deriving nothing skips it). `complete-all-tasks` checks before each dispatch, inline `complete-task` after the completion step 1; no write call, the completion procedure, or its agent gates. Reason: with no current mission the one-at-a-time hold moved per scope, exact where all missions stand at the root; a gate opening on less than a clear answer lets collisions through; a refresh before a closed gate goes stale, and a mission may start while a writer authors; completion checks catch overlaps a merge or late list brought, or a holder started mid-run. Retired forms: the pointer's hold at activation, a gate inside a write call.
- **The starting state is refreshed in place from an anchor in the log, and staleness never stops a run.** The section grounds every decider, is the as-of decisions are read with, and is what review finds gaps against. `starting-state-procedure.md` is one commit-free shape for first run and refresh, followed by `specify-mission-starting-state` and, in place, `derive-tasks` and `submit-task`, each committing `requirements.md` (and `open_questions.xml` when a pick was cleared) under `Starting-state: <MISSION_DIR>`, unvaried, since the anchor is the latest such commit, found by `since`, never stored. No print is a first run, the anchor alone unmoved ground (nothing explored, edited, or cleared; the skill's no-op line), more a refresh. It explores the scope, then adjacent material; reads `missions --mission`, then `summary` or `show` per bearing mission; and reads `live <MISSION_DIR>`, a started sibling's decisions and remaining tasks left to it, a defined one's goal alone. It reads no bar or `tasks --with-body`, for this section only, and keeps every still-true subsection byte-identical, touching no other section or decision. A refresh is a premise change: picks the changed facts undermine, by the hand-answer tests, doubt stripping, go in one non-transitive `strip --recommendation` keeping alternatives, a failed call re-run once before its fixed stop, the edit uncommitted. Only review weighs a decision against a changed fact, as an ordinary question. The writers check `since --missions` after their first gate, commit their refresh printing no line, explore nothing without an anchor, and re-examine no decision; the skill keeps the broad form; every chain opens with the refresh and a review pass. A no-change exploration records nothing, so a stale window re-explores each run, the cost of no state. A failed missions-tool call stops on the fixed line before any edit, ending a writer's run; a failed refresh commit stops it on its own line. Reason: an overlapping started mission finishes first, so the snapshot is stale at task entry by construction; re-exploring unchanged ground writes noise; a stop asks for what the writer can run; the narrow form spares a lone mission. With finish's context-file edit, the section protects an earlier mission's choices from a task. Retired forms: a stored anchor, a staleness stop, a refresh rerun by hand.
- **`alternatives-procedure.md` and `recommend-procedure.md` stay two files.** Only the pick half loads the principle store, a weighted advisory factor cited when it bore, never a filter or veto, and carries the sibling-disclosure duty and stale-set rule; the enumeration half forms no preference. Neither holds XML markup (the writing runners') or the what-would-change-your-mind layer (`discuss-open-question`'s). Reason: their grounding diverges. Retired forms: one merged core, markup in either.
- **An alternative set (`alternatives-procedure.md`) is distinct and covering, with no count.** Its step 2 names the decision's axes first (values from the decision, not the wording; a degree is an axis; each assumed premise an axis valued accept or reject; each axis has a none position), builds each option as one position on every axis, and tests distinct (any two differ in substance on an axis) and covering (the decision, not its wording; not doing the thing included where honestly viable, postponing a form of it, never a second option). The what-it-is states every axis position, unlimited, with no reasons. Growth stops upstream: review asks one choice per question, except mutually constraining ones, asked together with only viable combinations; no second-axis test is named; sibling-owned axes only appear as a drawback's condition. Reason: the set is the one menu every later pick chooses from, outliving later decisions, so a missed direction (near-duplicates, an answer no option held, an unlaid combination, a shared premise) is invisible downstream; stated positions make the tests checkable, and the what-it-is is what `lift --alternative` folds and capture reads. Retired forms: "typically two to four" or any count, which pads, trims, and hides growth.
- **Fold before remove.** In the answer core, rewrites and notes included, and each sweep section, chaining `fold` or `replace` before `remove` behind `&&`, the decision is written before the block goes. Reason: an interruption leaves the harmless superset, never a lost decision. Retired forms: the swapped order.
- **`remove` is the one reconciliation engine, and doubt strips.** Both inputs ride its one write. `--option`: the answer core passes the lifted id verbatim, never parsed from ANSWER; a literal answer passes one only on a prose verdict that it plainly settles on a block alternative. `--undermined`: picks a hand answer undermines, reconciled with tagged dependents in that write, transitively, alternatives kept, judged in `hand-answer-procedure.md` over the answer core, a pass-through recorder with one input and no branch; `answer-with-recommendation-procedure.md` and the sweep pass none. The judgment reads option and rationale against the answer (no longer doable, or its reason gone) without re-forming the pick, on every hand answer, a match with the block's own pick no exemption. The tool resolves every name first, refusing an unknown one or the block's own, and leaves a pick-less one alone. Reason: a tag is the only record of what a pick assumed, and an earlier pick cannot declare the answer, so unnamed the sweep records it as given; a strip costs a re-run, a stale rationale a wrong decision. Retired forms: a `reconcile` subcommand, a cascade clearing an `<alternative>`, an advisory or commit-body line for stripped dependents.
- **Tasks are briefs, and the completion procedure derives, verifies, and hands on the bar.** `derive-tasks` and `submit-task`, over `task-format.md`, write only a unique title and a 1–3 sentence brief. `complete-procedure.md` derives the bar, the whole `Task-completion:` body its runner records: one `- ` bullet per criterion, in verification order, as it passed, not re-derived or summarized, stated once in step 5 with no git step. The past-work read (`tasks <path> --with-body`, then `show <mission path>` where a task bears, full commands, whole print, no bound, pipe, or size rule) is discretionary, no measurement planned: on a file edited, not created (a delete, rename, or move counts, on its prior path), whose shape only this mission's goal, starting state, and decisions could explain, never the context file; at step 2 for the named files, a criterion it fixes naming its source in its bullet (the `tasks` hash, or the mission path for a `show` decision), and at step 3 before any other existing file, shaping the edit only. A failed call, `show` refusing `-` included, is the read not taken, never retried or a stop, no fixed line: inline, prose quoting the `Error:` line; the agent says nothing. An earlier decision or bar the brief would undo, unaddressed here, governs how the work is done wherever the brief can still be met; only where every way undoes it does the brief win, as the later-recorded decision, with no stop or flag. A finding changing a later queued task goes through step 3's fixed `replace`, never the running section, riding in this commit, adding no path, bar line, or git step. `complete-task` is the one skill and agent pair, inline vs. isolated; `submit-task` is skill-only; `derive-tasks` delegates nothing. Reason: the diff holds the brief and the subject the title, so subject plus bar is the handover, nothing re-typed, and a bar in a task file reads as an authoring contract; the read stops a task undoing by accident an earlier mission's choice, a layer above the starting state, so skipping it costs no protection; `record` printed 434 lines for one file where `tasks` printed 39; a step-3 re-derivation lets the bar drift. Retired forms: `Steps`, `Provides`, `Notes`, `Success` sections; the `**Verified:**` label or any body line beyond the bar; a bar in a task file; `record` for the read.
