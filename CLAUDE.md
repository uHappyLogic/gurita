# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A plugin (`gurita`) for Claude Code, Antigravity, and Codex that brings a mission's important questions up to be decided before work starts, so execution can then be handed to agents. It ships as a set of skills, a few agents, shared procedures, and the stdlib-only Python tools under `tools/` (among them the open-question tool and the task-list tool, the only writers of each mission's open-question document and of its task list once they are created, the read-only missions tool through which the live missions are listed from the tree and finished missions and completed tasks are read back from their commits, and the fold tool through which the answer sweep records its decisions in `requirements.md`) that move a project from a vague idea through discussion, planning, completion, and archival — mission by mission.

```bash

uv run scripts/build_hosts.py --check                   # drift gate: fails if the committed hosts/ trees differ from a fresh build
uv run pytest                                           # Python tool suite under the pinned interpreter (.python-version)
uv run --no-project --python 3.9 --with pytest pytest   # the same suite at the 3.9 floor; run both before committing a tool change
uv run pytest host_tests --host <host>                  # on-demand host suite driving the chosen host's installed CLI against that host's installed plugin copy, <host> exactly one of claude, antigravity, or codex; run against each host whose trigger set a change touches (CONTRIBUTING.md ## Development)

uv run scripts/render_banner.py                         # regenerate assets/banner.svg from assets/banner.txt and banner-colors.txt after any change to the drawing, then rebuild hosts/

(source "$HOME/.nvm/nvm.sh" && nvm use 22 && cd gurita-vscode && npm ci && npm test)          # the VS Code extension's build dependencies and node:test unit tests; Node runs only through nvm, Node 22

```

## Skills and the workflow they encode

The skills form a linear pipeline, every skill working inside one mission given its path as a required leading `--mission <path>`; `docs/skill-reference.md` describes each one and `docs/workflow.md` the phases. Each skill's SKILL.md is its exact behaviour.

```
init-mission-base-workflow          ← one-time bootstrap of the context file's ## Mission Workflow guidance only, replacing an older section whole and carrying the principle store to the root in that pass; probes nothing; commits under Workflow-bootstrap: missions
discuss-mission-goal                ← conversational, creates nothing; reads the record and proposes the mission's --at scope
define-mission-goal                 ← checks git, then python3 ≥ 3.9; creates <scope>/mission_<slug>/ with its three files from a required --at
specify-mission-starting-state      ← fills "Relevant starting state", or refreshes it in place once since prints past the anchor, through the shared procedure; clears the picks a refresh undermines
review-mission-requirements         ← repeatable loop engine and sole author of <open-question> blocks; reads the missions overview; reports convergence
provide-alternatives-to-all-open-questions ← annotating pass 1: one read-only subagent per block lacking alternatives, embedded through the tool
recommend-all-open-questions        ← annotating pass 2: picks inline over the whole set, then sorts the document
discuss-open-question               ← conversation about one question; offers answer-open-question and modify-mission-goal
answer-open-question                ← records a literal answer (Manual-answer:)
answer-open-question-with-recommendation ← records one question's embedded recommendation (Recommendation-answer:), inline
answer-all-open-questions-with-recommendation ← inline sweep in the tool's walk order, dispatching no agent, one commit per answer
answer-open-question-with-alternative ← records a named embedded alternative (Alternative-answer:); skill only
modify-mission-goal                 ← edits ## Goal and clears the picks it undermines with one non-transitive strip, committed together; surfaces the rest, never cascades
derive-tasks                        ← decomposes requirements.md into brief-level tasks; precondition: no open question; checks the scope gate first and again before writing, refreshing a stale starting state in between
submit-task / discuss-new-task      ← ad-hoc task entry (author one brief, checking the scope gate first and again before inserting, refreshing a stale starting state in between / clarify into briefs)
complete-all-tasks / complete-task  ← orchestrator over the complete-task agent / inline single task; each checks the scope gate before a task
ask-in-mission-context              ← read-only Q&A
finish-mission                      ← removes the mission's directory in one Mission-finish: <path> commit whose body is its summary; capture is a conventional follow-up, never a precondition
capture-mission-principle-updates   ← on-demand harvester of one mission's answer commits into the principle store, given its path, removed ones included
```

## Mission file structure

Each live mission lives at `<scope>/mission_<slug>/`, directly in the directory holding the core of its work with no container between them (`mission_<slug>/` when that is the root), and contains exactly `requirements.md` (prose only: Goal, Relevant starting state, Decisions, Out of Scope, plus an optional fifth section, `## Noted contradictions`, between Decisions and Out of Scope, present only while a note stands and created by no tool — a single-question answer skill inserts its heading with the first note and the review pass deletes it with the last, so the mission-definition tool's template, headed `# <title>`, keeps the four), `open_questions.xml` (created empty with the mission, then written only by the open-question tool, in its canonical form; empty means converged), and `TASKS_TODO.md` (`##` headings + `---` separators; created with the mission, then written only by the task-list tool, in its canonical layout). A completed task leaves the list, and its whole record is its `Task-completion:` commit — the title in the subject, the brief as the section's removed lines in the diff, the verified bar as the body — read back through the missions tool's `tasks` query rather than from any file in the directory. No mission is current and no file says which ones exist: the directories the discovery pattern finds are the live missions, every one addressed by its path, and a mission is finished once `finish-mission` removes its directory, its whole record then its `Mission-finish: <path>` commit — the summary as the body, the three files at the commit's parent — read back through the missions tool's `summary` and `record` queries. The principle store stands at `answer_decision_principles.md` at the project root, in no directory, whatever scopes the missions use. Missions defined before the XML split (this repository's `milestone_01`–`milestone_27`) hold no `open_questions.xml`, and those defined before completed tasks moved into commits (`milestone_01`–`milestone_53`) one more file, `TASKS_DONE.md`; each such directory was removed, files and all, by its finish commit, so they stand only in history, as the pre-split invariant and the task-list invariant's pre-flip note describe.

## Invariants to preserve when editing skills

These are the design decisions a later editor must not "fix" back. The mechanics they name live in the runtime files, the tools and their tests, and `docs/`; only the rationale lives here.

- **The open-question tool is the only writer of `open_questions.xml` once it exists, not its sole reader.** The mission-definition tool creates the empty document with its mission directory; after that, every listing of or change to the question document is a tool call, invoked at every site as the one fixed command `python3 {{PLUGIN_ROOT}}/tools/open_questions.py <subcommand> <MISSION_DIR> …` (the resolved directory, never the file path; free text on stdin as a quoted heredoc; never `python`). A user-invoked skill running inline in the conversation, or a shared procedure followed by one, that needs the whole set to reason over reads the file directly, for reasoning only; a dispatched agent never does — dispatched agents reach the question document only through the tool. That ban's placement scopes it to this one document, so it needs no carve-out for the other files an agent reads whole (the `complete-task` agent reads `TASKS_TODO.md` whole, both agents read `requirements.md` whole as prose). Runtime prose states the tool's contract in at most one sentence per site and never restates escaping, indentation, boundary tokens, or reconciliation mechanics. The pre-milestone-27 `awk`/`sed`/`grep` boundary-line idiom stays retired. There is no hand-edit exception anywhere: a stale alternative set or pick is cleared with the tool's `strip` / `strip --recommendation` and a re-run. `add`, and `add` alone, refuses a new Short Title whose folded form holds `/`, `"`, `$`, a backtick, `\`, any control character (C0 and DEL), or a `.` followed by whitespace, or that opens with `-` or ends in `.`, with one `Error:` line naming what it found, the document unchanged, and the help text stating the rule, because a block's id is copied into positions that give those characters a meaning: the alternatives agent's return file name (a `/` names a directory, so the write fails on every run and the block stays bare for good), the double-quoted shell argument every fixed call writes the title into (where `"` ends the argument, `$` and a backtick expand, and `\` escapes, while the calls are run exactly as shown with no escaping rule), the positional argument no fixed call writes `--` ahead of (a leading `-` reads as an option, `-h` printing the help and writing nothing), the hand-answer skills' separator, the first `.` followed by whitespace, which a title ending in `.` or holding a dot-space would end early, and the document itself, which a control character leaves unreadable. One check at the one point a title is created closes every position at once, so no fixed call gains an escaping rule or a `--`, and it refuses no title a person would write, dotted file names, inner hyphens, and the five entities staying legal; `load_document` keeps validating ids for duplicates only, so a block authored before the refusal still loads and is left to the operator's own `remove` and `add`. An alternative's id is created at `embed --alternatives` alone, which refuses one with one `Error:` line naming the id and the document unchanged on two grounds, both stated in the help text and checked independently of `add`'s rule. Its folded form holding `"`, `$`, a backtick, or `\` is refused because the id is copied as the option into the same double-quoted shell arguments a title is (the sweep's `--option`, `lift --alternative`, `<recommendation option>`), while `/` stays legal since an id names no file; the `provide-alternatives-to-open-question` agent's rendering rule names those four characters as ones an id may not hold, so the refusal does not spend the return's one repair. Its folded form holding a spaced em dash ` — ` is refused because `lift` joins option and rationale with exactly that separator and every reader of the joined line takes the text before its first one as the option — the compact view's `"${pick%% — *}"`, the sweep's literal copied from that print, and RECORDED OPTION in `answer-with-recommendation-procedure.md` and `answer-open-question-with-alternative` — so `Wait — then decide` passed both embed forms, was cut to `Wait`, and had its `lift --alternative` refused; one check where the id is created closes all three parse sites with them and `lift`'s line left exactly as they are, and the agent's rule names no dash, so an agent writing one spends its one repair on it. `embed --recommendation` needs no check of its own, its option already having to name one of the block's ids, and ids already embedded stand, since loading a document checks no id character.
- **The task-list tool is the only writer of `TASKS_TODO.md` once it exists, and changes no read of it.** The mission-definition tool creates the file with the mission directory; after that every write is one fixed command `python3 {{PLUGIN_ROOT}}/tools/task_list.py <subcommand> <MISSION_DIR> …` (`initialize` for `derive-tasks`, `insert` for `submit-task`, `remove` for the completion procedure, and `replace`, the fourth, for the completion procedure's rewriting of a later queued task's brief; free text on stdin as a quoted heredoc; never `python`), while every read of the list stays as it was — whole-file prose reads by the completion procedure, `complete-all-tasks`, `finish-mission`, `derive-tasks`, the triage skills, and `ask-in-mission-context` — because the reads never failed: the completion tail's section move was the one step runners rewrote as code each time (about three in four of 202 measured completion agents wrote an ad-hoc slicing script, one needing a second script to repair a blank line), so the `##`/`---` parsing moved into a tested tool and the chained call made the completion tail one turn. Runtime prose states the tool's output contract in at most one sentence per site and never restates its parsing or layout rules. Every write parses the whole file and renders it in one canonical layout, untouched sections included, because nothing ever checked the shared blank-line convention and drift is normalized silently on the first write rather than refused; the same render discards whatever stands above the first section and writes the file's fixed heading, never checking or refusing the preamble, since every writer commits its own write and a dropped line is in that commit's diff and recoverable by revert. A section ends at its `---` when one comes first and otherwise at the next heading or the end of the file, a section without one is accepted silently, and every section the tool writes carries its `---` (an insertion behind an unterminated section gets the separator that boundary needs). On re-parse a section's `---` is the one standing directly before the next heading or the end of the file — a `---` line is a separator only when the next non-blank line is a column-0 `## ` heading or the end of the file, every other `---` line is body text — and every column-0 `## ` line is a heading with no code-fence exemption: one bounded lookahead and no parser state, so a body `---` written verbatim never strands text between sections and no write refuses for it, while `insert`'s guarantee that piped body lines are never structure holds for its own call only. The tool matches every title (the section to remove or replace, a `--before`/`--after` anchor) by exact equality after whitespace- and case-folding, refusing a partial or shared title, because a tool that guessed could remove the wrong section; the case-insensitive partial match stays in procedure prose, where step 1 resolves the user's name against its own whole read, lists the headings on no match, and passes the full heading on. Title uniqueness is checked in `TASKS_TODO.md` only, the one file the tool reads, never against completed tasks, so follow-up work may reuse a completed task's title, each completion listed by `tasks` under its own commit. `insert` takes the title as an argument and only the body on stdin, composing the heading and the `---` itself, and every call states exactly one of `--end`, `--before`, `--after` in a required group with no default and no append subcommand, because position encodes dependency order and a call that forgot its position must fail (argparse's exit 2) rather than land silently at the end; an anchor naming no section is refused, and `submit-task` then stops quoting the `Error:` line. `initialize` reads the whole ordered list in the file's own section form in one process and replaces `TASKS_TODO.md` with no flag and no refusal for what it held, so the `Task-derivation:` commit records the list whole and in order or nothing, and what was replaced is already in the previous commit, its drop visible in that diff and recoverable by revert; the guard stays the skill's Preconditions line. `remove` takes out the one matched section — its heading, body, and `---` — and nothing else: it reads no stdin and no bar, renders the section nowhere, and neither reads nor writes any other file in the directory, because a completed task's record is its `Task-completion:` commit (see the task-altitude invariant), whose diff already holds the brief as the removed lines and whose body carries the bar, so a copy rendered into a second file would be text re-typed where it could drift. It replaced `move`, which appended the section and the bar under a `**Verified:**` label to a done file, and with the second file went the two-file atomicity `move` needed (the done file replaced first and its original bytes written back when the list's replace failed, a failed restore leaving a duplicate): `remove` replaces one file through the atomic writer, and a failure leaves `TASKS_TODO.md` byte-for-byte unchanged. Because `remove` reads no bar, the empty-bar refusal `move` gave moved into the completion calls' own shell test (see the return-contract invariant), so the tool gained no bar check of its own. `replace <MISSION_DIR> "<Task Title>"`, the new body on stdin as a quoted heredoc, is the fourth subcommand, because a finding in one task can change what a later queued task should say, and field runs rewrote the list by hand for want of a tool call (the draft's REVISE entry), each such hand edit a write the tool did not make, so the call keeps the tool the list's only writer: it rewrites the body of the one section its title matches, by the same exact folded match as `remove`, keeping the section's heading, its position, and its `---`, and refuses an unmatched or shared title or an empty body with the file unchanged, as the fold tool's `replace` rewrites one subsection. The title cannot change, since the tool takes no second title and a new heading would be a different task, which `remove` and `insert` already give; nor does `replace` check the title characters, a check made only where a title is created, so a section already holding a refused character is still rewritten. - **Committing is a property of the skill layer, and its mechanics live in the commit tool.** `core/tools/commit.py` runs the dirty-own-path guard, the path-scoped `git add`, and `git commit` with the paths as its pathspec, and `core/shared/commit-procedure.md` is reduced to that tool's one fixed command over PATHS, SUBJECT, and an optional BODY and REMOVALS, run as the step's one git tool call with no git command of the runner's own beside it; the execution-neutral shared procedures stay commit-free. That one call captures BODY once from a quoted heredoc in the group-fed form `{ body="$(cat)"; } <<'EOF'`, under the clause telling the runner to pick a delimiter line the text does not contain, and passes it on as `--body "$body"`, a caller with no BODY leaving out both the capture and `--body`, because the double-quoted `--body "<BODY>"` the procedure showed before let a backtick or `$` in the body expand and a `"` end the argument, while the bodies its callers record hold those characters (62 of the 99 finish commits carrying a body, 28 of 51 `Alternative-answer:` bodies, 10 of 34 `Manual-answer:` bodies), so each runner had been re-quoting a command it was told to run as shown; the form is the one the completion calls already used for the bar, the commit tool and its contract stayed unchanged, every caller following the procedure by reference (`finish-mission`, `answer-open-question`, the two lift-based answer skills, `capture-mission-principle-updates`) reaches it with no edit of its own, and `tests/test_commit_procedure_call.py` pins it. The pathspec is what makes a commit record exactly its own paths: a commit without one takes the whole index, so with two completion runs in one tree (checked on 2026-10-28) run B's staged files rode into run A's `Task-completion:` commit and B then found nothing staged, and an answer sweep or annotating pass of a mission preparing beside a live completion run would record that agent's staged task under its own subject; with the paths as pathspec whatever else the index holds, another run's staged change included, stays staged and out of the commit. Each git write repeats only when git exits 128, its fatal-error code and the one a held index, ref, or `HEAD` lock produces (git gives up on the index lock at once), while exit 1 (a hook's refusal, nothing to commit, a pathspec matching no file) passes on at once; only the exit status is tested and no message text is read, so the tool retries no hook and no runner classifies a failure. The schedule is one constant, a fixed short pause between a bounded number of attempts, a window of a few seconds with no override, so another run's ordinary write is absorbed while a lock a crashed process left surfaces as git's message rather than as a call that waits forever. The tool takes one optional input beyond paths, subject, and body: `--remove PATH`, repeatable, runs `git rm -r -q -- PATH` for each removal the index still holds, inside the same retry schedule and before the other paths are staged, and records the removals in the same pathspec commit, its dirty-own-path guard covering them and `git rm` refusing a file with an uncommitted change, so no uncommitted work is discarded; it exists because finishing removes a directory, and a `git rm` typed beside the call would be the hand-rolled git step the tool replaced and would sit outside the retry. Its two callers pass their removals through it as the commit procedure's REMOVALS, `finish-mission` its mission directory and `init-mission-base-workflow` the principle store's old path when it carries the store to the root, and a call without the option runs no removal and no read of one. Ahead of the path-scoped `git add` the tool asks git, one `git ls-files --cached --others -- PATH` read per named path run with optional locks off as the guard runs, which named paths the index or the working tree still holds, stages only those, skips the add when none is left, and keeps every named path in the commit's pathspec, which git matches against `HEAD` as well as the index: a path `git rm` or `git mv` already took out of the index is then recorded as the staged removal it is, where `git add` of it had exited 128 on all 16 attempts (`fatal: pathspec ... did not match any files`) and ended the call with nothing committed, so a runner may delete or move a file with `git rm`, `git mv`, or plain `rm` and `mv` alike, and the completion procedure has it record a deleted file's path and both the old and the new path of a renamed or moved file; a path git knows nowhere, a mistyped one, reaches the commit's pathspec unstaged and is still refused there with git's exit 1, passed on at once, so no mistyped path is silently dropped, and no call shape, path-file format, or `--remove` use changed. The retry rides on git's own lock, not on a lock of the plugin's own, which a crashed run would leave behind with no message saying how to clear it, nor on a per-run private index, which would leave the shared index stale. The mechanics are a tool rather than steps written into each call because a retry loop re-typed by every caller is the hand-rolled code the tools exist to replace (a plain shell loop exits 0 after its last failed attempt), and one tested tool also absorbs the guard, the pathspec, and the path-file read, lets the retry be tested against a held lock, and keeps the pause out of a shell sleep. The tool prints nothing when a commit lands and, exiting 0, exactly one fixed no-op line on stdout when none of the paths changed, because a no-op is a success as every sibling mutator's is and a routine no-op must not end a call on a status a runner reads as failure; every refusal or git failure is one `Error:` line on stderr, carrying git's message when a git command failed. The fixed-line rule extends past the success path, as one plugin-wide convention: every no-op and stop condition a skill states opens its report with one fixed, identifier-free line of its own, the whole first line, and whatever variable detail the condition needs follows on the lines below it — the tool's `Error:` line quoted verbatim, the Short Titles a precondition found, a remedy — so failure and clean-stop paths keep their full messages beneath that line. A condition is the check that ended the run, not the text of the refusal it relays: a tool call refused for any reason is one condition with one line, the `Error:` line beneath telling the reasons apart, so the runner never classifies an error's wording. Every line is unique across the plugin, a stop a shared procedure owns (the mission resolution's one, the scope gate's one, the completion procedure's task lookup) having one line in that procedure, printed by every runner following it, and the success line the three single-question answer skills share being one listed line. The reason is the headless chain: no skill sets an exit code, so a harness running the skills one invocation after another knows how each ended only from its final message, and fixed lines let it match the success and no-op lines that continue a chain, record which stop ended one, and keep matching across versions. The lines are a listed contract rather than prose: `docs/skill-reference.md`'s `## Fixed console lines` table lists every success, no-op, and stop line, and that convergence line as its one verdict line, with its source and kind, and `tests/test_fixed_console_lines.py` checks each listed line verbatim against every rendered host tree, as a whole line of a fenced block or a whole inline code span, and checks that no line repeats, so a line changes only together with its row. A message a fixed call prints to its own runner mid-run, never as a report's first line — the orchestrator's `path file empty`, the answer sweep's `dirty before start`, and `acceptance bar empty`, the one shared text both completion calls print when their test refuses an empty bar, a retry prompt for the runner — is outside the table, which is why that guard added no row and left the table, its preamble, and its test unchanged; the two fixed-call tests pin the message by behaviour instead. The alternatives pass's advisory carries, besides each `FAILED:` and post-repair skip and each failed commit, the result of one closing `list --without-alternatives` call after the run's last batch: every gathered id it still prints that is not already in the advisory goes in under the fixed reason `no annotation landed`, because no `DONE` is cross-checked against the scan and that print is the only place a file that never landed shows; the same print chooses between `Alternatives embedded.` and the no-op lines, so the status line is read from the document rather than from a count the orchestrator would have to hold. The rule is authored inline at each site that prints a line, a skill's reporting step or the step that stops it, and in the shared procedure that owns a stop; there is no `report-procedure.md`.
- **Task altitude.** Authoring runners (`derive-tasks`, `submit-task`, both over `core/shared/task-format.md`) write only what cannot be re-derived: a unique title and a 1–3 sentence brief. No `Steps`/`Provides`/`Notes`/`Success` sections ever. `core/shared/complete-procedure.md` derives the acceptance bar itself and hands it to its runner, which records it as the body of the task's `Task-completion:` commit, so the bar lives in a commit body, never in a task file, where it could be read as an authoring contract. The body holds nothing beyond the bar — exactly its `- ` bullets, one per criterion, with no brief, no label line, and no other field — because the brief is already recorded as the removed lines of `TASKS_TODO.md` in the same commit's diff and the subject carries the title, so subject plus bar is the whole handover a reader's judgment needs and no text is re-typed where it could drift; the retired `**Verified:**` label must not come back as a body line. The bar's record form (one `- ` bullet per criterion, in verification order, each as it stood when it passed, neither re-derived nor summarized, a criterion the past-work read fixed carrying its source inside its own bullet) is stated once, in the procedure's step 5 beside the bare `remove`, worded as the form of the bar the procedure hands on and naming its destination only as the record the runner's own file writes, with no git step, commit, or body, so the procedure stays commit-free; the inline skill's call and the agent's body-file write show `- ` placeholders and refer to it, adding no rule of their own, and since the body is the bar alone that one sentence states the whole body's shape. A bullet may name its source because the commit body is the only place a past-work read that bore on the bar can show: every criterion the step-2 read fixes names what it was formed against inside its own `- ` bullet, the abbreviated hash from the `tasks` line when a task commit's diff or bar fixed it and the mission path from that line's third field when a decision `show` printed fixed it, the rule stated once in step 2, so each kind of evidence carries the identifier the read itself printed, the body stays the bar alone with no label or reference line beside it, and the read shows in every body `tasks --with-body` prints back. The step-3 read leaves no such trace, because it shapes the edit only and the bar, held verbatim from step 2, is never re-derived on it: a re-derivation when the record binds would let the bar change after it was derived, the drift the no-drift rule forbids, and add a second derivation path the runner would have to know when to take, while the step-2 read already gives the bar the decision wherever the task names its files up front. Where either read surfaces an earlier mission's decision or verified bar that the task as briefed would undo and this mission's `requirements.md` does not address, the earlier decision governs how the work is done wherever the brief can still be met, the runner taking a way of meeting the brief that leaves it intact, and the brief overrides it only where every way of meeting the brief undoes it, as the later-recorded decision of a converged mission, the order `derive-tasks` gives a conflicting pair; the read exists so that a task does not undo by accident what an earlier mission chose on purpose, and the accident is exactly the case where another way of meeting the brief exists, so the procedure gained no stop, no fixed line, and nothing flagged, and an unattended run gains no remedy it has no path to. `derive-tasks` delegates nothing; `submit-task` is skill-only; `complete-task` is the only skill+agent pair, differing only in inline vs. isolated. Every task-list runner resolves `<MISSION_DIR>` via `resolve-mission.md` and checks the scope gate via `check-scope-gate.md` before its work (see the scope-gate invariant).
- **`derive-tasks` resolves a conflicting pair by recording order and is never blocked by one.** Its precondition stays the empty `list`, so a note under `## Noted contradictions` never stops it; where two `## Decisions` entries cannot both hold, the later-recorded entry governs the brief, every noted pair taken as conflicting as noted without re-judging and any pair the runner finds itself resolved the same way, and nothing is flagged for either. The rule fixes which entry wins where task derivation already let one win silently: of the 20 field runs that printed the sweep's old contradiction advisory, 12 went straight to task derivation, where one entry won with both left standing (in this repository's `milestone_43` the later one is what shipped), and no revert followed any advisory, so a flag would be an advisory nobody acts on and a block would make the run wait on a section the convergence check never reads. Later-recorded is read from the commit that added each entry's lines (blame or a pickaxe search path-scoped to `requirements.md`), never from file position, because a decision lands in whichever subsection fits rather than at the end of the file, so position says nothing about when it was decided, and never from the note, which records a pair, not its order.
- **Environment context comes from `CLAUDE.md`** (`AGENTS.md` in the Antigravity and Codex trees, through the `CONTEXT_FILE` slot; `/init` once per project) for the starting-state procedure (followed by `specify-mission-starting-state` and, refreshing, by `derive-tasks` and `submit-task`), `derive-tasks`, and the completion procedure. The bootstrap writes only its `## Mission Workflow` section into that file, from `core/shared/workflow-guidance.md`, the one home of that section, and never the environment context.
- **Dispatched-agent return contracts.** A `FAILED` from the `complete-task` agent promises a resumable tree (partial work continued, never redone or reverted), not an untouched one — do not restore the old promise; it writes neither the body file nor the path file and stages and commits nothing. A failed past-work read is never a `FAILED`: the agent treats either call failing, `tasks` or a `show` follow-up, whatever the reason, as the read not taken, carries on from `requirements.md`, the context file, and the live material, and reports nothing about it, since its only final messages are `DONE` and `FAILED:`, a read it may skip altogether must not end an unattended run over a slip as small as a mistyped path, and a git-level fault still stops the task at the scope gate or the commit; the procedure states this in a clause of its own because its opening rule, to diagnose, fix, and retry and never skip a step, would otherwise push the agent to return `FAILED:` (see the missions-tool invariant). The `complete-task` agent's success return is two files beside its last-line token, its bar and its change set never travelling in a message: `complete-all-tasks` creates its run's scratch directory once with `mktemp -d` before the first dispatch, and on `DONE` the agent has written its acceptance bar to `<scratch dir>/body.txt` and its task's whole change set — the paths the completion procedure's running list recorded plus `<MISSION_DIR>/TASKS_TODO.md`, one path per line, never built from `git status` or any tree-wide selection — to `<scratch dir>/paths.txt`, both chained behind its `remove`'s `&&`, with no payload above the bare `DONE`. The body file is the one place the bar crosses a process boundary: the agent derived and verified it, the orchestrator holds no work context and must not re-type it, and its commit-from-file call already reads one file the agent wrote, so the bar rides as a second fixed-name file beside `paths.txt` that the same call passes as `--body` and moves into `processed` with it. The agent's step-5 call opens exactly as the inline skill's does, capturing the bar once and testing that it holds a non-blank line ahead of `remove` behind `&&`, and only after `remove` succeeds writes the body file and then the path file, so nothing reaches the scratch directory unless the test and the removal both pass, both runners share one bar-handling form, and the write-nothing-else contract holds with no carve-out; an empty bar prints the call's one line and removes, writes, and commits nothing, and the runner fixes the bar and runs the call again, as it once did after a refused `move`. The orchestrator's call guards the crossing with `body file absent` and `body file empty` tests beside its two path-file tests, copying the pattern it already ran on the path file, each committing nothing and stopping the run under the existing `Task run stopped — a completed task could not be committed.` line with the task name and the test's own line below it, so no new fixed line was needed. The task list rides in the path file because the agent's fixed call already names it beside its recorded paths, so the file is the task's whole change set and the orchestrator's call names no path of its own, only the file. The names are fixed per run, written by every task's agent and taken from no task title, because a heading holding a slash or a double quote, both present among this repository's recorded headings, would otherwise end a run with its work done and its list unwritten; the orchestrator's commit call moves both files, once read and whatever the commit's outcome, into a `processed` subdirectory under names `mktemp` makes unique there, costing no turn and deleting nothing, so the fixed names are absent when the next agent starts, a missing file is detectable, and every task's bar and list stay on disk. The alternatives agent's return is a file, not a message. Its one write, the sole exception to its read-only contract, is `<scratch dir>/<Short Title>.xml` in the run's scratch directory, which the orchestrator creates once per run with `mktemp -d` (fresh and uniquely named under the system temp location, so no stale return or concurrent run collides with it; the same wording in every host tree, so it adds no slot; writable under Codex's workspace-write sandbox, which keeps `$TMPDIR` and `/tmp` writable by default). The agent writes under a temporary `.xml.part` name and renames into place with one `mv`, so a wake-up scan running while other agents still write never pipes a half-written file (the rename stays inside one directory, hence atomic). Its only final messages are the bare token `DONE` or `FAILED: <reason>`. The file is what stops a return travelling through the orchestrator's context twice — once arriving as the agent's final message, once re-typed into a heredoc for `embed` — so the orchestrator never holds a return at all. The final message is a token rather than the file's path because the path is fixed at dispatch (the Short Title exactly as given plus `.xml`, in a directory the orchestrator created), so the batch derives each title from the file name and has nothing to copy; a Short Title holding a path separator, which only a block authored before `add` refused such a title can carry, fails the write and surfaces as a `FAILED:` skip whose reason names the separator rather than a silent miss. The orchestrator's only judging is the last-line `FAILED:` verdict, which gets no repair; everything else is one fixed batch shell call that scans exactly the `*.xml` files directly inside the run directory, redirects each unedited into `embed --alternatives` (the tool slices and validates), commits each accepted question, prints one line per refused file or failed commit, and moves every piped file, accepted or refused, into a `processed` subdirectory, so no file is piped twice and the record of what was piped lives on disk, never in the orchestrator's context. Every refusal one batch call prints gets its one repair at once, all sent together in the same turn — continue the same agent session while its handle is still held, one fresh re-dispatch only once it is gone, the branches and the wait on the repairs written per host in the `ALTERNATIVES_REPAIR` slot — and the repaired file lands at the same path for a later batch with no special handling; whether a question has had its repair is the only thing tracked, and a second refusal or `FAILED:` is the per-question skip. A wait that returns before every awaited agent has ended waits again, without limit, so an expiry never skips a question. No `DONE` is cross-checked against the scan: a cross-check would need the per-agent list the batch exists to keep out of the orchestrator's context, and the closing `list --without-alternatives` call already catches every question whose file never landed, whatever its message said, leaving its block bare for the next run. The orchestrator deletes nothing — no scratch file, `processed` subdirectory, or run directory — and no delete or recursive-remove command enters the runner's prose, so a headless chain never meets a permission prompt for one and a refused return the advisory names stays on disk for inspection; the system's own temp handling reclaims the directory. The batch replaced, in milestone 43, the per-return pipeline, which judged, piped as a heredoc, repaired, and committed each return the moment it landed: across 21 measured runs that cost about 16 post-dispatch orchestrator turns per run, more than half of them text-only or silent, at a median 57k-token context with every return held twice, against an estimated 0.82M input tokens per mission that batching and the smaller context save (1.17M counting one outlier run). Do not restore the per-return pipeline, a returned path, a `DONE` cross-check, or a cleanup step. The rule under both forms — pipe the whole unedited return to the tool, repair once, then skip — deliberately reversed the earlier discard-whole rule (eight of ten milestone-19 dispatches were lost to a grounding preamble), and the extraction moved into the tool in milestone 27; do not restore skip-only behaviour or move extraction back into prose. The batch pattern is scoped to that one agent: the one other dispatch site, `complete-all-tasks`, keeps a last-line token as its verdict and reads its agent's two fixed-name files only after a `DONE`, with no scan, repair, or batch, and the recommendation pass and the answer sweep dispatch nothing and have no return to judge.
- **A dispatch prompt carries only what the orchestrator already holds and the agent cannot fetch itself.** This holds for both dispatched agents without qualification: `complete-all-tasks` passes the task's `##` heading text, the resolved `<MISSION_DIR>`, and the run's scratch directory and nothing else, the alternatives orchestrator passes the question's Short Title, the resolved `<MISSION_DIR>`, and the run's scratch directory and nothing else, and each agent fetches the rest under the mission directory itself (its task section; its own block by `locate` and its sibling scope by `list --with-question`; `requirements.md`). The mission directory passes the rule at both sites because the agent cannot fetch the orchestrator's resolution: the `--mission <path>` the orchestrator was given reaches the agent no other way, and nothing stored could tell the agent which of several live missions the orchestrator commits for, so both prompt fences carry it as one fixed `Mission directory: <MISSION_DIR>` line on every dispatch, one unconditional prompt shape at both sites, and the agent uses it as given with no resolution of its own. The scratch directory passes the rule at both sites because the agent cannot fetch it: each orchestrator creates its own with `mktemp -d` once per run, and both prompt fences carry it as one fixed `Scratch directory: <scratch dir>` line on every dispatch, the same directory for every agent of the run, passed on every host, unconditionally, so the prompt templates and the agent files stay host-neutral with no branch on whether the value is present. The body file added no prompt line: it lands in that same directory under its own fixed name beside `paths.txt`, so the `complete-task` prompt kept its three lines, and the bar travels in neither direction through a message — the orchestrator passes none, since the agent derives its own, and receives none in the agent's final message, the bar landing in the body file that the agent's empty-bar test and the orchestrator's body-file tests guard. The orchestrator holds no work context, so every extra slot is something it would have to gather and hold per dispatch only to hand over, and a value the agent can fetch is delivered twice when copied into the prompt (under the retired prompt with a `Question block:` slot the alternatives agent read its block in the prompt and again in its whole read of `open_questions.xml`); a fetch also gives the agent the live document rather than the orchestrator's snapshot. The retired `Question block:` slot and the orchestrator's per-question `locate` gather must not be restored, and the two `list` calls are the pass's whole gather. The rule constrains the prompt, not the agent's reading: what an agent may read whole is fixed per document by the invariants above.
- **Skill frontmatter.** Every SKILL.md and agent carries `name` and an unquoted `description` of one clause, 25 words or fewer, no colon or semicolon, loadable by `yaml.safe_load`; it is a routing label, never a record — provenance, mechanics, cross-references, and trigger lists are cut outright (their home is `docs/skill-reference.md`). No exceptions to the cap; an agent description keeps its invocation contract as a short clause.
- **Runtime files carry no editor-facing prose and name no host.** They hold only what the runner needs. The rule covers every rendered runtime file, slot values included: a value names no host, its own included, and reaches its host's mechanism through that host's own identifiers (tool names, config keys, file and command names), otherwise saying "this host" (the agents' Claude-only `color` key is stripped by the Antigravity and Codex definitions' data, the one structural exception). With it goes a development rule: a rendered tree never names another host's mechanism, in any file — the files rendered from `core/` and the host's own templates (README, CONTRIBUTING pointer, manifest, marketplace file, traffic workflow) alike, a contrastive mention of what this host does not use included; a link to the source repository is not a mechanism naming. It is a rule, not a check: `host-name-in-core` keeps scanning `core/` only, so a slot value or template that breaks it passes the build and is caught in review. A host's hands-on check is recorded in one place only, the dated block in the header comment of that host's `settings.toml`, naming the installed version checked and the points and values the run covered, which a later re-check updates; the comment above each slot entry says only what the value stands for and why, in mechanism terms, with no version, and no tool version or observed-behaviour fact enters this file. No `## Rules` sections: a rule lives in the step it constrains or in the opening paragraph. Rationale lives here. The tool sources follow the same rules (no bare `{{`, no host name even in a comment, no placeholder of their own) so each renders byte-identical into every host.
- **Host wording differences are named slots, never markers, duplicated files, or capability-conditional prose.** A sentence or phrase that differs between hosts is a `{{SLOT_NAME}}` placeholder in `core/`, filled from every definition's `[slots]` table; the `slot-declaration` check keeps the declared name sets identical across hosts and each name used in `core/`, and `unfilled-placeholder` catches a slot a host leaves undeclared. A slot is preferred over capability-conditional prose: `core/` never names a capability and leaves the runner to pick a branch at run time, because a branch the host lacks is dead text in its tree that a runner can still follow, so each host's tree describes only its own mechanism. Each value is written from that host's own hands-on check, never copied from another host's, and the trees of two hosts are not expected to agree: no byte-identity between host trees is kept or tested, and the build's rendering is tested by `tests/test_build_rendering.py` instead. The convention is one value file per slot under the definition's `slots/` subdirectory, bound inside `[slots]` as `NAME = { file = "slots/NAME.md" }` with the slot's comment above its entry, every value of every host held that way, the one-word and empty ones included; the build still accepts the inline string form and nothing refuses it, so the file form is a convention, not a check. A value carries no placeholder other than `{{PLUGIN_ROOT}}`, which is why `AGENT_TOOL` and `ALTERNATIVES_AGENT` were retired: their wording is written literally inside each host's `ALTERNATIVES_REPAIR` value. The alternatives pass's host-dependent passages are slots: `ALTERNATIVES_PARALLELISM`, the opening paragraph's phrase saying whether the per-question dispatches run together; `ALTERNATIVES_REPAIR`, the opening of the repair sub-step ahead of its fixed corrective message, fill rule, and one-repair cap (which stay in `core/`), holding the repair branches this host has and how the run waits on the repairs; and `ALTERNATIVES_CONCURRENCY`, the paragraph opening step 3, which also governs how the pass collects returns. Each host's `ALTERNATIVES_CONCURRENCY` is one single-mechanism paragraph describing only that host's dispatch and wait: the Claude Code and Antigravity values send every dispatch at once, none blocking, and run the batch call each time the run wakes with landed returns, no shell loop or event monitor serving as the wait; the Codex value dispatches rounds of at most the session's `agents.max_threads` cap, calls `wait_agent` until the round's last final message has arrived before batching once, and gives a refused round's repair set its own wait and batch before the next round, so repairs never share a wait or take a slot. `ALTERNATIVES_CONCURRENCY` and the repair wait in `ALTERNATIVES_REPAIR` are the pass's only host-dependent waiting wording; no slot was added for the batch, and the scratch directory, the dispatch prompt, and the agent file are host-neutral. The Antigravity values dispatch both agents by the bare names the tree's own `agents/` directory carries, with no file or build change added for agent loading. Codex runs both agents as its generic subagent told to read and follow the plugin's Markdown agent file, with no TOML file, registration step, or format conversion in the build, because Codex documents no way for a plugin to ship a custom agent.
- **Pre-split missions** (`milestone_01`–`27`) get no compatibility: they hold no `open_questions.xml`, and each directory was removed like every other finished mission's, by its finish commit, so they stand only in history, at those commits' parents, where `git show` and capture's diff walk reach them; their files are not converted, and a question skill pointed at such a directory, restored from history or still standing in another project, stops on the open-question tool's `Error:` line.

## Development

The build loop, both test runs, the version bump, and the distribution repositories are documented in `CONTRIBUTING.md` under `## Development`; the release procedure in `.claude/skills/release-plugin/SKILL.md`. Points not recorded there:

- `hosts/<host>/` trees are pure build output: rebuild after any change under `core/` or `scripts/hosts/` and commit the rebuilt trees with that change, so `main` always passes `--check`. `--check` is run by a maintainer or CI, never a git hook; the CI workflow has no path filter (a `paths` list would be a hand-maintained copy of the build's input set) and is one job, never a matrix.
- The floor run bypasses the build tooling's `requires-python = ">=3.11"` on purpose; the tools need nothing from that project. Two bracketing runs replace a version matrix because stdlib availability is monotone across minors. The literal `3.9` has three homes: the README prerequisite, the `define-mission-goal` check, and the CI floor run. `tests/test_build_rendering.py` is the suite's one pinned-only test: the build imports `tomllib` and PyYAML, so the module skips itself at module level below Python 3.11, keyed on the interpreter version and before any import of the build, and the floor run reports it skipped while the pinned run never does; no pytest command, `conftest.py`, or `pyproject.toml` setting excludes it. It renders a synthetic `core/` through one synthetic definition in-process and covers rendering and the file-backed slot refusals, not `main`'s orchestration or the check set.
- Adding a host means adding a definition directory under `scripts/hosts/`; no host-specific Python exists. A host definition's `[layout]` must map all four `core/` directories, every one inside its `plugin_dir` (the path from the tree root to the runtime plugin root: empty for Claude Code and Antigravity, `plugins/gurita` for Codex), and it must declare every wording slot the other definitions declare, each value held by convention in its own file under the definition's `slots/` subdirectory (which template discovery skips), the inline string form still accepted.
- `set_version.py` writes nothing under `hosts/` (manifests are rendered from `VERSION` by the build). `/release-plugin` makes one `Release: <VERSION>` commit that changes only version slots and the `CHANGELOG.md` entry, then publishes each host tree with `git commit-tree` into `uHappyLogic/gurita-<host>`; those repositories and every `traffic-data` branch are never hand-edited. `TRAFFIC_TOKEN` is a fine-grained PAT on exactly the four repositories, kept in no local copy.
- Outside contributions are proposal-first (see `CONTRIBUTING.md`): the maintainer reserves the mission by running `/define-mission-goal --at <scope>` with the accepted goal on `main`, choosing the scope, its `Mission-definition: <path>` commit being the reservation; the contributor branches from that commit, runs the pipeline with `--mission <path>` through `/finish-mission`, whose removal commit carries the mission's record, syncs by merge only, and the pull request, whose template names the reserved path, is merged as a merge commit so the mission commits survive for release notes and capture. An abandoned contribution is cleaned up by reverting the definition commit.

## Mission Workflow

This project uses the mission-driven workflow. Each mission lives at
`<scope>/mission_<slug>/`, directly in the directory holding the core of its work, with
`requirements.md`, `open_questions.xml`, and `TASKS_TODO.md`. No mission is current: every
skill working inside one is given its path as `--mission <path>`, exactly as
`/define-mission-goal` printed it, trailing slash included.
A mission directory is removed only by `/finish-mission`, whose `Mission-finish: <path>`
commit carries the mission's record, so the directories standing are the live missions and
the git log holds the finished ones.
