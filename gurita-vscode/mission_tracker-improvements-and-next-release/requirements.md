### Extension layout, build, and tests

`gurita-vscode/` is a TypeScript project compiled by `tsc` with no bundler. The host modules stand flat under `src/`, and the two webview scripts, `src/webview/page.ts` for a mission page and `src/webview/settings.ts` for the Settings window, draw everything through DOM calls inside one shared page shell whose stylesheet is written inline (`pageShell` in `src/pane.ts`). Three stdlib Python scripts ship beside the compiled output: `runner.py`, `harness_check.py`, and `install_plugin.py`. `scripts/bundle.js`, run by `vscode:prepublish`, copies `core/tools/missions.py` and `shipped_recipes.md` into the git-ignored `bundled/` and writes `fixed_lines.tsv`, from the `## Fixed console lines` table of `docs/skill-reference.md`, and `plugin_version.txt`, from `VERSION`, beside them. The tests are 27 `node:test` files under `src/test/`, the page tests running the compiled page scripts against a stand-in DOM (`fakePage.ts`), and 8 pytest files under `runner_tests/`; CI runs `npm ci`, `npm test`, and `npm run package`.

It also stands in the hover text of the side-bar view's two mission-starting rows (`Recipe: <name>`), in error notifications such as `No recipe is named <name>.`, in the description of the setting `gurita.ownRecipesFile`, and throughout the listing README. The shipped file's recipe section is the `## Recipes` heading the reader looks for (`RECIPE_SECTION`).

### Recipe sources and stored state

The reader reads two recipe files, the shipped one and one per-user file, `~/.gurita/recipes.md` or the path the user setting `gurita.ownRecipesFile` (scope `application`) names, with the per-user variant store `~/.gurita/variants.json` laid over them; no recipe file is read from the project. The one project file a run reads is `task_line_rules.txt` at the project root, read by `runner.py` for the looped run. The variant store, the picked defaults, and the selections remembered in `workspaceState` are keyed by recipe name, and stored variants of a recipe name the files do not hold form a recipe of their own, listed last in the own group.

### Mission page

A mission page (`drawPage` in `src/webview/page.ts`) stacks the workflow diagram, which has no heading, the `Recipes` section, a looped run's preview while one stands, the New task row, and the two pane headers, Open questions and Remaining tasks, over the selected pane. The page draws neither the mission's title nor its goal: the title reaches the editor tab and the page's `aria-label` only, and the extension reads no `requirements.md` (`src/documents.ts` reads `open_questions.xml` and `TASKS_TODO.md`). The recipe buttons stand side by side in one wrapping row, each showing its recipe's name and the selected variant's name with the variant's lines as its hover text and an arrow-only variant dropdown beside it, and the row holds only the recipes whose `Stage:` fits the step the diagram fills, beside every undeclared one. While a run started for the mission is going, the page disables every action button and pulses the diagram's filled block, and no text says why. The Remaining tasks pane lists the `##` headings alone (`parseTaskHeadings` in `src/tasks.ts`; `runner.py` holds its own read of each task's title and brief, for the rule file), and a completed task is shown nowhere, the extension calling only `live` of the bundled missions tool.

### Question card

The Open questions pane shows one card at a time under a pager of Previous, a counter such as `3 / 12`, and Next, the left and right arrow keys moving likewise. The card's head carries Discuss, Answer, and Answer with recommendation, each a fixed-name button with an arrow-only variant dropdown beside it (`QUESTION_BUTTONS` in the page script, `PAGE_BUTTONS` and `BUTTON_RECIPES` on the host side). Each alternative carries an Answer with this alternative button and a dropdown of its own on one line with the alternative's id, its selection remembered per mission, question, and alternative. Every text on the card, the question, the pick's rationale, and each alternative's text, advantages, and drawbacks, is set through `textContent`, so backticks show literally.

### Typed values

Every value a run needs is asked for by `askValues` in `src/pane.ts` through `vscode.window.showInputBox`, one single-line box per value: the answer text, the goal, the scope, the issue description, and the optional discussion note. The Settings window asks for names and list entries the same way, at three sites in `src/settingsWindow.ts`. The recipe-variants mission recorded that the pages hold buttons and dropdowns only and that nothing is typed on a page anywhere in the extension.

### Runs and refresh

Every run is `runner.py` started as a terminal's own process (`shellPath` `python3`, `isTransient`). After every chain and every looped run, finished or stopped alike, it prints its report and `Press any key to close this terminal.` and waits for a keypress (`wait_for_key`), a chain then exiting 0 when it ran every line and 1 otherwise; the extension learns that a run ended only from `onDidCloseTerminal`, and until then the mission's page stays disabled. The first-version mission recorded the reason: VS Code disposes such a terminal the moment its process exits, so the runner keeps its process alive. The manifest contributes one setting, `gurita.ownRecipesFile`. The session's one file watcher covers `**/mission_*/{requirements.md,open_questions.xml,TASKS_TODO.md}` with a 300 ms debounce and git state is not watched, although a mission's next step and review-round count are read from `git log` (its `Requirements-review:` commits) and its `started` or `defined` from `missions.py live`; the Refresh command re-reads everything.

### Side-bar view and commands

The Missions view (`src/missionTree.ts`) is a native tree of leaf rows with no child rows: New mission and Define mission above one row per live mission, with `No mission is live.` or the live read's failure shown through the view's `message`. A finished mission leaves the view, and a window still open on it shows `This mission is no longer live.` A Define mission run belongs to no mission: when its terminal closes the live missions are re-read and the new mission appears as a row, and no window opens by itself. The manifest contributes six commands, of which the Command Palette offers `gurita.refreshMissions` alone, the other five, `gurita.openMission` among them, hidden by `when: false` entries as the activity-bar mission decided, and the listing README states that besides the side-bar view there is no entry point. The view shows nothing about the plugin's install state or the project's context file.

### Harness check and Codex

`harness_check.py` checks Claude Code, Antigravity, and Codex (the CLI found, a Gurita copy installed, its version at least the packaged one). The extension runs it on the first opening of the Settings window in a session, on Check again, and after an install or update run, keeps the result for the session, and shows a failed check in the Settings window alone, where Install and Update stand. The Settings window holds Codex's model list, read from `-m` on `codex` lines, and no effort list, and a line's harness dropdown offers Claude Code and Antigravity only (`SWITCHABLE_HARNESSES` in `src/lineValues.ts`, `LINE_HARNESSES` in the Settings page script), a `codex` line keeping its harness as text. The runner counts `$gurita:` as a skill invocation, so a `codex exec '$gurita:<skill> …'` line is headless; that is the form `docs/ways-of-using.md` gives for Codex, with `--dangerously-bypass-approvals-and-sandbox` as the counterpart of `--dangerously-skip-permissions`. ### Plugin facts the entries rest on

The bundled `missions.py` is the whole missions tool, so `gate`, `tasks --with-body`, `missions`, and `summary` are in the package, uncalled. A held scope stops `derive-tasks`, `submit-task`, `complete-task`, and `complete-all-tasks` on `Scope gate closed — the scope is held or could not be checked.`, the scope counting as held whenever `gate <path>` prints anything. The answer sweep stops on `Sweep stopped — the mission files already held changes.` when `requirements.md` or `open_questions.xml` holds an uncommitted change. `init-mission-base-workflow` takes no argument and writes the `## Mission Workflow` section into the host's context file, `CLAUDE.md` on Claude Code and `AGENTS.md` on Antigravity and Codex. `capture-mission-principle-updates` takes the mission's path as a positional argument, a finished mission's included, and no `--mission`, while `ask-in-mission-context` takes `--mission <path>` and the question and resolves a live mission only.

## Decisions

### Naming

- **Renamed chain lines.** Under its new name, "Approve all standing recommendations and review again", the shipped recipe keeps its `default` variant with every line unchanged (the answer sweep, a review pass, the alternatives pass, and the interactive recommendation pass), and that variant becomes the recipe's only one. The `Mixed-agent (Gemini reviews, Claude annotates)` variant is removed from `gurita-vscode/shipped_recipes.md` altogether, with no replacement: it is neither reordered to fit the name nor moved into a recipe of its own.

- **Recipe word outside buttons.** The texts the user meets while working with missions say "action": the mission page's failure line, the error notifications, and the hover text of the side-bar view's two mission-starting rows (`The actions could not be read.`, `No action is named <name>.`, `Action: <name>`). The texts that describe configuration keep "recipe": the description of the `gurita.ownRecipesFile` setting and the README's prose, the README stating once that each recipe in a recipe file is shown as an action where it is fired and as an action recipe in the Settings window.

- **Stored state after rename.** State a user stored under `Requirements iteration` is left as stored, with no migration and no alias: the variant store format, `overlayVariantStore`, `variantEdits.ts`, and the `workspaceState` selections stay unchanged. Stored variants under the old name, stored copies of its `default` or mixed-agent variant included, form a recipe called `Requirements iteration` in the own group, which declares no `Stage:` and so is listed on every mission page. A hiding record or picked default under the old name matches no variant, so the renamed recipe shows every shipped variant and opens on its first. A remembered selection is kept only while that orphan recipe still lists the variant it names, and is otherwise dropped as one naming a gone variant. The listing README says that nothing carries stored state over to the new name, as it already says for the one-block variants renamed `default`, and the user moves it by hand in the Settings window.

### Mission page

- **Long goal display.** The mission page's introduction shows the mission's title alone by default, with one control beside it that shows and hides the whole goal beneath it. The goal is collapsed on every load of the page, so no shown or hidden state is saved, and the control is present whatever the goal's length, with no clamp and no overflow measurement.
- **Completed tasks placement.** The completed tasks stand inside the page's second pane, beneath the remaining task list, behind one show/hide toggle that is collapsed by default. That pane's header is renamed from "Remaining tasks" to "Tasks", a name covering both lists, and the remaining tasks head their own part of the pane. The page keeps its two pane headers and the default-pane rule, and gains no third pane.

### Runs

- **Auto-close default.** The new setting that closes a run's terminal by itself ships on. A chain that ran all its lines closes its terminal without waiting for a keypress and unblocks the mission's page, while a chain that stopped keeps waiting for a keypress. A user who wants every terminal to stay open turns the setting off.

### Recipes and harnesses

- **Codex line effort.** A Codex line carries its effort as the config override `-c model_reasoning_effort=<level>`, the `--config` spelling read as well, and `lineValues.ts` reads and replaces that value as it does `--effort`. The Settings window gains a Codex effort list under Models and efforts, built like the other two: taken from the values the shipped recipes, own recipes, and stored variants carry, with the person's `addedEfforts`/`removedEfforts` overlay on top. A Codex line gets both a model dropdown and an effort dropdown. A line switched to Codex keeps its effort when Codex's list offers it and takes the list's first effort otherwise, written as the override, and a Codex line switched back to Claude Code or Antigravity keeps or maps its effort the same way.

### Release

- **Release within the mission.** The task list holds no release task, and the mission is finished before 0.3.0 is published: `/finish-mission` removes the mission's directory in its `Mission-finish:` commit, and the maintainer then runs `/release-vscode-extension 0.3.0` by hand. The skill drafts its notes from this mission's finish summary, read as a mission finished since `gurita-vscode-0.2.0`, beside any other extension mission finished by then. The release is the step that follows the mission, not its last step, and the goal's closing clause is revised to say so.
