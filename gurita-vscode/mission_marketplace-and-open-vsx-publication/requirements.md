# Marketplace and Open VSX publication

## Goal

Publish Gurita for VS Code as `uhappylogic.gurita-vscode` on the Visual Studio Marketplace and on Open VSX, so it installs from the Extensions view of VS Code and of the forks that read Open VSX; the mission ends with the extension live on both. The steps only the maintainer can take, creating the publisher and the namespace and issuing the tokens, are the mission's first tasks, and the package gets what a public listing needs: a user-facing README, an icon, and listing metadata. Releasing a version of the extension becomes a maintainer-only skill of its own beside `/release-plugin`, through which the first publication is made, and the check comparing the installed plugin's version with the packaged one stays as it is.

## Decisions

### Release skill

- **Publish site and tokens.** The extension's release skill builds and publishes from the maintainer's machine, running the pinned `vsce publish` and an `ovsx publish` in its own shell, and starts no GitHub Actions workflow. Both tokens are kept as environment variables named `VSCE_PAT` and `OVSX_PAT`, the names both command-line tools read without a flag, exported from the maintainer's shell profile so that every session started from that shell has them, and the skill passes no token on any command line. The skill checks that both variables are set and prints how to set them when one is missing. Nothing is stored in the repository or on GitHub.
- **Release skill name.** The extension's release skill is `.claude/skills/release-vscode-extension/SKILL.md`, run as `/release-vscode-extension`, with `name: release-vscode-extension`: the verb `release` and the object `vscode-extension`, which names the editor family. `/release-plugin` keeps its name.
- **Extension release tag.** An extension release creates a lightweight tag with a fixed prefix of its own, `gurita-vscode-<VERSION>` (for example `gurita-vscode-0.2.0`), on the commit the release is built from, and pushes it. Both of `/release-plugin`'s lookups of the last plugin release gain a positive pattern that only the bare plugin form matches, `git describe --tags --abbrev=0 --match '[0-9]*'`, with the same `--match` beside `--exclude=<VERSION>` on a resumption, so any tag that does not start with a digit is ignored. The extension's release skill finds its own last release with the mirror call, `--match 'gurita-vscode-*'`. The 37 existing plugin tags are left as they are.

- **Version source at release.** The extension's release skill takes the version as a required bare `MAJOR.MINOR.PATCH` argument, as `/release-plugin` does. After its checks pass it writes that version into `gurita-vscode/package.json` and `package-lock.json` with `npm version <VERSION> --no-git-tag-version`, run through the nvm Node 22 wrapper inside `gurita-vscode/`, so npm makes no commit and no tag, and the version is written before the skill packages and publishes.

- **Extension changelog.** The extension gets a changelog of its own, a tracked `gurita-vscode/CHANGELOG.md` holding one entry per extension release, newest first. It sits at the extension root, where `vsce package` picks it up by name with no flag, so the VSIX carries it and both the Marketplace and Open VSX show it on their changelog tabs. The root `CHANGELOG.md` stays the plugin's release notes only, and `/release-plugin` is not changed for it.

- **Bundled plugin state.** An extension release may be built only from a `main` whose three bundled sources (`core/tools/missions.py`, `docs/skill-reference.md`, `VERSION`) are byte-identical to those at the tag named by `VERSION`; the extension's own code may sit anywhere after that tag. The release skill checks this before it changes or publishes anything and, on a mismatch, stops on a fixed line that names the differing files and the remedy: release the plugin first with `/release-plugin`, or wait. `scripts/bundle.js` and builds made by hand stay unrestricted.

- **Release commit subject.** An extension release makes one commit of its own, holding only what the release writes into the tree (the extension's version slots and any changelog entry), under a marker of its own that does not open with `Release:`: `Extension-release: <VERSION>`, the version being the whole descriptor. The skill recognises its own interrupted run by a `HEAD` subject of exactly that string, as `/release-plugin` recognises its own, and `/release-plugin` is left untouched.

- **Extension GitHub release.** An extension release creates no GitHub release, in `uHappyLogic/gurita` or anywhere else on GitHub. It publishes the package to the Visual Studio Marketplace and to Open VSX only, and the repository's releases page goes on holding plugin releases alone.

- **Release pre-flight checks.** Before it writes or publishes anything, the extension's release skill runs a fixed set of hard stops, each ending the run with nothing changed and the reason reported, and none ever waived. Repository state: the tracked tree is clean, `HEAD` is on `main`, `main` is not behind `origin/main` after a fetch, and no untracked file stands under the extension's source paths outside its git-ignored build directories. Toolchain: Node 22 answers through nvm, `npm ci` installs the pinned dependencies, and `vsce` and the Open VSX publishing tool both resolve. Tests: the extension's `node:test` suite (`npm test`) and the runner's `runner_tests/` pass. Build: `npm run package` builds the VSIX into the ignored `dist/`. Tokens: each registry's token is checked live against that registry for the `uhappylogic` publisher or namespace, through the verify-token command each publishing tool offers, which also confirms that the publisher and the namespace exist.

- **Half-published release.** A re-run of the release skill with the same version asks no registry anything. It runs both publishes again, each with the `--skip-duplicate` flag that the pinned `vsce` 4.1.1 and `ovsx publish` both offer: the registry that already holds the version turns its publish into a silent success, and the other receives the version from a package rebuilt from the state the version was released from. The same two publish commands, flag included, serve the first run and every re-run, with no registry query and no branch.

- **Pre-publish confirmation.** The release skill pauses exactly once, on every run, after its pre-flight checks and all local work and before anything public: the first registry upload and any push or tag the release makes. The pause shows the version about to be published and the release notes in full, verbatim, as they will be published. It accepts three answers, as `/release-plugin`'s step 7 does: an explicit publish proceeds, a stated revision of the notes is applied and the version and notes are shown again, and anything else stops with nothing public done. The pause is never skipped and no flag bypasses it.

- **Open VSX tool source.** A release gets `ovsx` from the extension's own Node project: it is added to `devDependencies` in `gurita-vscode/package.json` at an exact version, beside `@vscode/vsce` 4.1.1, and recorded in `package-lock.json`, so `npm ci` in `gurita-vscode/` installs it into `node_modules/`. The release skill runs the local binary (`npx ovsx publish` or `node_modules/.bin/ovsx`) through the nvm Node 22 wrapper inside `gurita-vscode/`, as it runs the pinned `vsce publish`.

### Listing README

- **Listing screenshots.** The README the listings show carries one animated GIF near its top showing the extension at work: a sample mission opened from the side-bar view and a recipe or looped task run progressing in a mission window. It is generated by an automated script that captures the flow from VS Code, never recorded by hand, tracked in the repository under `gurita-vscode/`, referenced from the README by a relative path the packager resolves against the repository's raw files, and regenerated by re-running the script when the flow it shows changes. The README carries no banner and no still screenshot.

- **Listing README file.** The README the listings show is `gurita-vscode/README.md`, rewritten for a person installing from a listing and still packaged by vsce's default README lookup. Its Requirements, Building and packaging, and hand-install sections move into a new tracked file in `gurita-vscode/` for building from the checkout (for example `BUILDING.md` or `CONTRIBUTING.md`), which is kept out of the VSIX through `.vscodeignore` and which the README links to by an absolute repository URL. `CLAUDE.md`'s pointers that send the reader to `gurita-vscode/README.md` for the package build are repointed to the new file.

- **Demo recording step.** Generating the GIF is one ordinary agent task on the list, placed before the first publication, and not a maintainer-only task. The agent writes a tracked script under `gurita-vscode/scripts/` that seeds a sample project and mission from the host suite's fixture project, launches VS Code with a throwaway profile and the extension loaded, opens the mission from the side-bar view, starts a recipe run against a stand-in for the harness CLI placed first on `PATH`, so the run is deterministic and uses no model session, captures frames, and assembles them into the GIF. The agent runs the script, and the script and the GIF land together in that task's `Task-completion:` commit. The task's bar checks that the script exits cleanly, that the file stands at its path, opens with a GIF signature, and stays under a stated size bound, that it is the path the listing README references, and that the captured frames show the intended flow. No test compares the committed GIF with the generator's output, because a capture is not reproducible byte for byte.

- **Listing README depth.** The README the listings show carries the extension's whole use documentation: every use section `gurita-vscode/README.md` holds today (the side-bar view and its rows, the mission windows, the Settings window with the harness check, harness enabling, model and effort lists, variants, and single-task lines, the recipes with the shipped recipe file and the user's own, the looped task run and its rule file, and the runner), at its present depth. Only the passages addressed to someone building from the checkout, such as how the activity-bar icon is regenerated, are taken out or reworded. It sends the reader nowhere else for how to use the extension, so it needs no link to further documentation.

### First publication

- **Listing verification.** Nothing is observed after publication. The extension counts as live on both registries once the release skill's two publish commands, `vsce publish` for the Marketplace and `ovsx publish` for Open VSX, have both exited successfully. The mission opens no listing page, queries no registry, and installs the published extension in no editor, VS Code or a fork, to confirm it.

- **First published version.** The first publication carries a pre-1.0 version above `0.1.0`, such as `0.2.0`, written into the manifest and both sites of `package-lock.json` before it is packaged. Versioning stays the extension's own, separate from the plugin's `VERSION`, and the extension stays in the 0.x range that signals an interface still settling.

### Publisher and namespace

- **Open VSX namespace ownership.** The mission claims ownership of the `uhappylogic` namespace on Open VSX, but only as far as filing the claim. The claim is filed with the first maintainer-only tasks, directly after the namespace is created, and that task counts as done once the claim's issue exists. The mission records nothing further about it and ends whether or not the claim has been granted: publication does not wait for the claim, and granting is left to Open VSX outside the mission.

- **Maintainer-only tasks.** The account steps stay tasks on the list, and the maintainer takes them by hand before the task run starts: creating the Marketplace publisher `uhappylogic` on the web, creating an Eclipse account and signing the Open VSX publisher agreement, and issuing both tokens. The task the runner then completes, the agent or the inline one alike, is verification only, with whatever can be scripted once a token exists done by the runner, creating the Open VSX namespace through `ovsx create-namespace` among it. Its bar holds three checks: the publisher and the namespace exist, observed through a registry query; each token is accepted by its registry for `uhappylogic`, through `vsce verify-pat` and `ovsx verify-pat`; and each token stands where the release skill will read it. When a check fails the agent returns `FAILED:` with what the maintainer must still do, the run stops before any later task, and a re-run once the steps are taken completes the task. The task's commit records the bar and the task list's removal only.

### Listing icon

- **Listing icon design.** The listing icon shows the activity-bar icon's three arms as filled outlines in the same geometry, filled white or the activity bar's near-white `#d7dae0`, on a filled square in the banner's darker violet `#9333ea`.

- **Listing icon production.** A stdlib-only Python script under `scripts/` (a new renderer or an extension of `scripts/render_icon.py`) rasterizes the listing icon itself from tracked plain-text drawings and writes it as a PNG through `zlib` and `struct`, with no external tool. The PNG is committed under `gurita-vscode/media/`, named by the manifest's `icon` entry, regenerated by re-running the script and never edited by hand. A pytest test beside `tests/test_icon.py` checks that the committed file is a well-formed PNG of the listing size and equals what the generator produces.

### Listing metadata

- **Listing name and description.** The manifest's `displayName` stays `Gurita for VS Code`, and its `description` is rewritten as one sentence for a reader new to the plugin: it says what Gurita is (a plugin for Claude Code, Codex, and Antigravity that settles a mission's questions before handing its work to agents), what the extension adds (a side-bar view and windows over the plugin's missions, questions, and recipes), and that the plugin must be installed for it to do anything.

- **Listing categories.** The manifest's `categories` is replaced by `AI` as its only entry, one of the twenty categories the installed VS Code 1.143.0 recognizes, so both listings place the extension under AI and no longer under `Other`.

- **Preview flag.** The extension is published as a regular release. The manifest gains no `preview` entry, the extension goes out through the ordinary release channel on both registries, and neither listing carries a Preview badge. Nothing in the manifest or the release skill marks the extension's maturity beyond what its version number says.

- **Issue and question links.** The manifest's `homepage` names `https://github.com/uHappyLogic/gurita/tree/main/gurita-vscode#readme`. The mission adds an extension bug form under `.github/ISSUE_TEMPLATE/`, asking for the extension's own version, the editor and its version, and the platform; `bugs` names it directly through `https://github.com/uHappyLogic/gurita/issues/new?template=<form>.yml`, and the form also appears in the issue chooser. `qna` names `https://github.com/uHappyLogic/gurita/discussions/new?category=q-a`.

- **Listing keywords.** The manifest gains a short `keywords` list of about six to ten entries: the extension's own terms (`gurita`, `missions`), the three harnesses the plugin runs on (`claude code`, `codex`, `antigravity`), and a few domain terms naming what it does (`ai agents`, `planning`, `requirements`).

- **Gallery banner.** The manifest gains `"galleryBanner": { "color": "#9333ea", "theme": "dark" }`. The header band of the Marketplace listing page is the banner's darker violet, the same colour as the listing icon's square, with light header text (white on `#9333ea` is about 5.4:1).

### Package and platforms

- **Engine floor for forks.** The published package lowers `engines.vscode` to the oldest VS Code base among the Open VSX forks the extension means to reach, looked up when the change is made. `@types/vscode` is re-pinned exactly to the newest published typings not above that floor, and the extension is compiled and tested against them. The floor then stays fixed until a change needs a newer API.

- **Windows installs.** The package stays universal and installable on every platform, and the README states the limit. The extension gains a check at activation: on native Windows (the platform is `win32` and the window is not a remote one) it shows one message saying it runs only on macOS, Linux, or through Remote-WSL, and leaves its view, windows, and runner inert instead of letting them run. In a Remote-WSL window the extension runs on the Linux side, so the check never fires there.

- **Target Open VSX forks.** The extension means to reach four editors that read Open VSX and carry an agent of their own: VSCodium, Cursor, Windsurf, and Antigravity. The engine floor is the oldest of their four bases, looked up when the change is made, and `@types/vscode` is re-pinned to the newest typings not above it. Other Open VSX readers (Kiro, Trae, Theia, code-server, Gitpod) are not named and are reached only where their base meets that floor.

### Root documents

- **Root documents mention.** After the first publication the root `README.md` gains a short subsection with links to both listings and to `gurita-vscode/README.md`, and `CONTRIBUTING.md`'s `## Development` gains a pointer: the extension under `gurita-vscode/` has a build and test loop of its own (Node 22 through nvm, independent of the host build and `VERSION`), documented in its README, and is released through its own maintainer-only skill rather than `/release-plugin`. `docs/` stays untouched.

### CI

- **CI for the extension.** The existing `drift-gate` job gains a Node setup (`actions/setup-node`, pinned to a SHA, Node 22) and then `npm ci`, `npm test`, and `npm run package` in `gurita-vscode/`; the last of these runs `vscode:prepublish`, which compiles, runs `scripts/bundle.js` from the checkout, and calls `vsce package`. The built VSIX is discarded, and CI stays one job with no path filter.
