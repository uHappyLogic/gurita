# Marketplace and Open VSX publication

## Goal

Publish Gurita for VS Code as `uhappylogic.gurita-vscode` on the Visual Studio Marketplace and on Open VSX, so it installs from the Extensions view of VS Code and of the forks that read Open VSX; the mission ends with the extension live on both. The steps only the maintainer can take, creating the publisher and the namespace and issuing the tokens, are the mission's first tasks, and the package gets what a public listing needs: a user-facing README, an icon, and listing metadata. Releasing a version of the extension becomes a maintainer-only skill of its own beside `/release-plugin`, through which the first publication is made, and the check comparing the installed plugin's version with the packaged one stays as it is.

### The plugin's release skill, `/release-plugin`

`.claude/skills/` holds one skill, `release-plugin/SKILL.md`, maintainer-only and project-local, outside `core/` so no host tree renders it, and the single place the plugin's release procedure is documented. Run as `/release-plugin <MAJOR.MINOR.PATCH>`, it writes nothing until its pre-flight stops (a clean tracked tree, `main` not behind `origin/main`, the drift gate, each distribution repository and its token present, the host suite) and its version checks have passed, composes the notes from the missions finished since the last tag through `missions.py missions .` and `summary`, and makes one `Release: <VERSION>` commit changing only version slots and the `CHANGELOG.md` entry. It pauses once for the maintainer's confirmation, then publishes by check-then-do steps (push `main`, push the tag, create the GitHub release, publish each `uHappyLogic/gurita-<host>` repository), so a re-run with the same version resumes an interrupted release. Where a repository or token is missing it prints the commands the maintainer must run and exits, running none of them. No step of it builds, versions, or publishes the extension.

## Decisions

### Release skill

- **Publish site and tokens.** The extension's release skill builds and publishes from the maintainer's machine, running the pinned `vsce publish` and an `ovsx publish` in its own shell, and starts no GitHub Actions workflow. Both tokens are kept as environment variables named `VSCE_PAT` and `OVSX_PAT`, the names both command-line tools read without a flag, exported from the maintainer's shell profile so that every session started from that shell has them, and the skill passes no token on any command line. The skill checks that both variables are set and prints how to set them when one is missing. Nothing is stored in the repository or on GitHub.
- **Release skill name.** The extension's release skill is `.claude/skills/release-vscode-extension/SKILL.md`, run as `/release-vscode-extension`, with `name: release-vscode-extension`: the verb `release` and the object `vscode-extension`, which names the editor family. `/release-plugin` keeps its name.
- **Extension release tag.** An extension release creates a lightweight tag with a fixed prefix of its own, `gurita-vscode-<VERSION>` (for example `gurita-vscode-0.2.0`), on the commit the release is built from, and pushes it. Both of `/release-plugin`'s lookups of the last plugin release gain a positive pattern that only the bare plugin form matches, `git describe --tags --abbrev=0 --match '[0-9]*'`, with the same `--match` beside `--exclude=<VERSION>` on a resumption, so any tag that does not start with a digit is ignored. The extension's release skill finds its own last release with the mirror call, `--match 'gurita-vscode-*'`. The 37 existing plugin tags are left as they are.

### Listing README

- **Listing screenshots.** The README the listings show carries one animated GIF near its top showing the extension at work: a sample mission opened from the side-bar view and a recipe or looped task run progressing in a mission window. It is recorded by hand from VS Code and converted to GIF with a local tool, tracked in the repository under `gurita-vscode/`, referenced from the README by a relative path the packager resolves against the repository's raw files, and re-recorded when the flow it shows changes. The README carries no banner and no still screenshot.

- **Listing README file.** The README the listings show is `gurita-vscode/README.md`, rewritten for a person installing from a listing and still packaged by vsce's default README lookup. Its Requirements, Building and packaging, and hand-install sections move into a new tracked file in `gurita-vscode/` for building from the checkout (for example `BUILDING.md` or `CONTRIBUTING.md`), which is kept out of the VSIX through `.vscodeignore` and which the README links to by an absolute repository URL. `CLAUDE.md`'s pointers that send the reader to `gurita-vscode/README.md` for the package build are repointed to the new file.

### First publication

- **Listing verification.** Nothing is observed after publication. The extension counts as live on both registries once the release skill's two publish commands, `vsce publish` for the Marketplace and `ovsx publish` for Open VSX, have both exited successfully. The mission opens no listing page, queries no registry, and installs the published extension in no editor, VS Code or a fork, to confirm it.

### Publisher and namespace

- **Open VSX namespace ownership.** The mission claims ownership of the `uhappylogic` namespace on Open VSX, but only as far as filing the claim. The claim is filed with the first maintainer-only tasks, directly after the namespace is created, and that task counts as done once the claim's issue exists. The mission records nothing further about it and ends whether or not the claim has been granted: publication does not wait for the claim, and granting is left to Open VSX outside the mission.

### Listing icon

- **Listing icon design.** The listing icon shows the activity-bar icon's three arms as filled outlines in the same geometry, filled white or the activity bar's near-white `#d7dae0`, on a filled square in the banner's darker violet `#9333ea`.

### Listing metadata

- **Listing name and description.** The manifest's `displayName` stays `Gurita for VS Code`, and its `description` is rewritten as one sentence for a reader new to the plugin: it says what Gurita is (a plugin for Claude Code, Codex, and Antigravity that settles a mission's questions before handing its work to agents), what the extension adds (a side-bar view and windows over the plugin's missions, questions, and recipes), and that the plugin must be installed for it to do anything.

- **Listing categories.** The manifest's `categories` is replaced by `AI` as its only entry, one of the twenty categories the installed VS Code 1.143.0 recognizes, so both listings place the extension under AI and no longer under `Other`.

- **Preview flag.** The extension is published as a regular release. The manifest gains no `preview` entry, the extension goes out through the ordinary release channel on both registries, and neither listing carries a Preview badge. Nothing in the manifest or the release skill marks the extension's maturity beyond what its version number says.
