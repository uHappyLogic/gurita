# Activity bar view and per-mission windows

## Goal

Restructure Gurita for VS Code around an activity-bar entry. Its side-bar view is a native tree listing every live mission with its title, the workflow step to run next, its counts of open questions and remaining tasks, and a marker while a run is going, and it carries the controls that belong to no mission: New mission, Define mission, Refresh, and Settings. Clicking a mission opens that mission's own window in the editor area, several open at once, each showing one mission's page with no tab row; Settings opens as a window of its own, reachable from the side-bar view and from every mission window. The activity-bar icon is generated by a script from the README banner's drawing, as three of its arms, a large one in the centre and a smaller one on each side, and `ideas/vscode_extension.md` is removed as pre-prototype thinking the extension has outgrown.

## Relevant starting state

### The manifest and the entry point

`gurita-vscode/package.json` contributes two commands, `gurita.openMissionPane` (Gurita: Open Mission Pane) and `gurita.refreshMissionPane`, and one setting, `gurita.ownRecipesFile`, and activates on `onCommand:gurita.openMissionPane` alone. It holds no `viewsContainers`, `views`, `menus`, or `icon` entry, and no image file stands anywhere under `gurita-vscode/`. `src/extension.ts` registers the two commands and the run listeners and does nothing else at activation, so the Command Palette is the only entry point: there is no status bar item, menu entry, or keybinding, nothing opens by itself, and with no `WebviewPanelSerializer` registered the pane does not survive a restart or a window reload. The manifest declares `engines.vscode` `^1.143.0` and the build pins `@types/vscode` 1.140.0.

### The one mission pane, `src/pane.ts`

The extension holds exactly one webview panel (`gurita.missionPane`, titled Gurita Missions), created in the active editor column with scripts enabled and `retainContextWhenHidden` off, and a second run of the command reveals it. Everything the pane knows is module-level state of that one panel: the panel itself, the latest live read (`current`), what the latest answer posted (`posted`, which every click is checked against), the failure cause, the file watcher and its debounce queue, a stale flag, each mission's loop preview, and the harness check, all cleared when the panel is disposed. Each answer is one `live` message carrying every live mission with its documents, workflow step, default pane, recipe list, and fixed-name buttons, beside the paths of the missions with a running runner, or one `liveFailure` message carrying the cause. `pageShell` builds the page once, a content security policy with a nonce, the whole stylesheet inline, and the one script `out/webview/page.js`.

### The page script, `src/webview/page.ts`

One script, a single closure of about 1,800 lines, draws everything from the extension's messages: a row of tabs, one per live mission showing its title with its path as a tooltip, ending in **Refresh**, **New mission**, **Define mission**, and **Settings**, and beneath it the selected mission's page, the line `No mission is live.`, the one failure state, or the settings view. A mission's page (`drawPage`) is the workflow diagram, the Recipes list, a looped run's preview when one is held, and the two panes Open questions and Remaining tasks behind one row of two headers. The selected mission and each question view's position are saved with the webview's `setState`, the clicked pane header is held in memory only, and a tab click also posts `missionTab`, on which the extension brings that mission's run terminal forward. Every action button on a page is drawn disabled, and the diagram's filled block pulses, while a run started for that page's mission is going.

### What the extension reads about each mission

`src/live.ts` runs the bundled `missions.py live` from the project root, the top level of the git work tree holding the first workspace folder, and yields each live mission's path, `started` or `defined`, and title. `src/documents.ts` reads each mission's `open_questions.xml` and `TASKS_TODO.md` in process into the list of open questions and the list of remaining task headings, or a notice in place of either when its file is missing or does not parse. `src/workflow.ts` chooses the step to run next (`nextStep`) from that state, those documents, and git's count of `Requirements-review:` commits: first review round, additional review round, derive tasks, execute tasks, or finish, and none when a read the choice needs failed. The seven steps' names as drawn stand in the page script (`WORKFLOW_BLOCKS`), six of them also in the recipe reader's `STAGE_NAMES`, and nothing draws a count of open questions or of remaining tasks except the question view's position counter.

### Runs and the running note, `src/runs.ts`

Each run is a terminal whose own process is the bundled `runner.py`, and `RunningRuns` notes which mission's run is going from its start until the person dismisses its terminal, exposed as `runningMissions()`. `registerRuns` calls a `started` and an `ended` listener, on which `src/extension.ts` posts the running paths to the pane and, at the end, re-reads it. A run started by **New mission** or **Define mission** belongs to no mission and is noted for none. A click for a mission whose run is going is refused with a notification and that run's terminal shown.

### Refresh and file events

A `FileSystemWatcher` over `**/mission_*/{requirements.md,open_questions.xml,TASKS_TODO.md}` is created with the first live read that succeeds and disposed with the panel, its events debounced by 300 ms (`src/refresh.ts`): a change to a question document or task list re-reads that mission's documents, and a created or deleted `requirements.md` or a changed `TASKS_TODO.md` also re-runs `missions.py live`. While the panel is hidden an event only marks it stale, and it is re-read when shown. The **Refresh** control and `gurita.refreshMissionPane` re-read everything, and git state is not watched. All of it exists only while the panel does: with no pane open the extension reads no mission and watches no file.

### The controls that belong to no mission

**New mission** runs the recipe `discuss-mission-goal` with a typed goal, and **Define mission** the recipe `define-mission-goal` with a typed goal and then a typed scope, each value asked for in VS Code's own input box (`askValues`). Each button's label shows the harness, model, and effort of the variant it runs, and a dropdown beside it offers its recipe's variants, the selection remembered once per project. Both stand at the tab row's end with **Refresh** and **Settings** and are drawn in the failure state too. Their runs start at the project root the latest answer read, else at the git top level of the first workspace folder, else in that folder.

### The settings view

The settings view is part of the mission pane's page: the **Settings** control swaps it in beneath the tab row, **Close settings** or a tab click swaps it out, and no command opens it. Each opening posts `settingsOpened`, which the extension answers with the harness states, the model and effort lists, the variants, and the single-task lines, all read afresh, and the harness check runs on the first opening after the panel is created, its result kept in the pane's module state for the panel's lifetime. Every edit made in the view posts those lists again and the mission pages with their recipes re-read (`postPages`), to the one panel. The view holds buttons and dropdowns only.

### What is remembered

The variant selected in a dropdown on a mission's page is kept in `workspaceState` under `gurita.variantSelections`, a map from mission path and recipe name to variant name, and the two mission-starting buttons' selections under `gurita.projectVariantSelections`, a map from recipe name to variant name. Stored variants, each harness's enabled state, and the model and effort overlays are kept in the per-user file `~/.gurita/variants.json`. Nothing records which pane, mission, or view was open, beyond the page's own `setState`, which lasts while the panel stays open.

### The banner drawing and its renderer

`assets/banner.txt` is 96 columns by 10 rows of printable ASCII holding eight arms in four pairs of 23 columns each, every pair a shorter arm whose curl ends on row 8 and a longer one whose curl ends on row 10, the right two pairs the mirror image of the left two, so from left to right the arms run short, long, short, long, long, short, long, short. Every arm is drawn at one character scale, a stem of `o` suckers between brackets ending in a curl, ten to twelve columns wide in all, and the two heights differ by two rows. `assets/banner-colors.txt` gives the upper stems violet `#a855f7`, the lower stems and curls darker violet `#9333ea`, and the suckers and the dashes on the top edge slate `#64748b`. `scripts/render_banner.py`, stdlib-only and run by hand, takes any drawing path, reads `<stem>-colors.txt` beside it, and writes `<stem>.svg` beside both: one `text` element per row of `tspan` runs in a system monospace font stack on a grid of 10 by 20 pixels per cell, with no background, no embedded font, and no glyph converted to paths. `tests/test_banner.py` pins `assets/banner.svg` to the generator's output, the host build copies that file into every host tree, and nothing under `gurita-vscode/` reads `assets/`.

### The editor's API and its icon rule, as installed

Checked on this machine on 2026-11-23: VS Code 1.143.0 is installed with `uhappylogic.gurita-vscode@0.1.0`. Its `vscode.d.ts` and the pinned `@types/vscode` 1.140.0 both declare `window.createTreeView` and `window.registerTreeDataProvider`, a `TreeItem` with `label`, `description`, `tooltip`, `iconPath` (a `ThemeIcon` there may carry a `ThemeColor`), `command`, and `contextValue`, a `TreeView` with `title`, `description`, `message`, and a numeric `badge`, and a `WebviewPanel` whose `title` and `iconPath` can be set, `createWebviewPanel` making a new panel on every call. The installed editor's manifest schema describes a `viewsContainers` icon as "Icons are 24x24 centered on a 50x40 block and have a fill color of 'rgb(215, 218, 224)' or '#d7dae0'. It is recommended that icons be in SVG, though any image file type is accepted." The extension uses none of the tree API today.

### Known gaps

The extension has no activity-bar container, side-bar view, tree data provider, or menu contribution, and no icon or script that derives one from the banner. No drawing of three arms exists, and none of an arm at a larger scale than the banner's. Nothing in the pane's code addresses one mission's page or the settings view apart from the one panel: its state is module-level, one message carries every mission, and the settings view is drawn inside the mission pane's page. The `vscode` stub of the pane tests stands in for no tree API.

## Decisions

### Windows

- **Restore after a reload.** The mission windows and the Settings window that were open come back after a restart or a window reload, in the editor group and tab position they held. The extension registers a `WebviewPanelSerializer` for the mission window's view type and one for the Settings window's, and the manifest carries an `onWebviewPanel:` activation event for each. Each mission window keeps its mission's path in its webview state and is redrawn on restore from a fresh read of the live missions for that path, its `setState` values coming back with it; the Settings window is redrawn from fresh reads, as each opening reads them today. A restored window that is first shown while a window for the same mission, or the Settings window, is already open is closed, and a restored window whose saved state is missing or cannot be read is closed rather than drawn.
- **Run terminal on window activation.** Each time a mission's window becomes the active editor while that mission's run is going, the extension brings that run's terminal forward without taking the focus (`terminal.show(true)`). The trigger is the window becoming active by any route, a click on its row in the side-bar tree, a click on its editor tab, or keyboard navigation between editors, read from the panel's `onDidChangeViewState`. The focus stays with the window because a terminal that took it would deactivate the window and trigger the reveal again on the next click back into it. The row click does nothing of its own beyond opening or revealing the window, neither the side-bar tree nor the mission's page draws a control for bringing the terminal forward, and a click for a mission whose run is going is still refused with a notification and that run's terminal shown.

- **Open windows while the live read fails.** While the read of the live missions fails, every open mission window replaces its whole page with the one failure state today's pane draws, the line `The live missions could not be read.` with the cause beneath it. No mission's diagram, recipes, or panes stay drawn, so no action on them can be clicked against a failed read, and no per-window state is added. Each window stays open throughout and draws its mission's page again on the next live read that succeeds.

- **Mission window tab title.** A mission window's editor tab is titled with the mission's title alone. While another live mission carries the same title, every colliding tab gains its mission's scope after a separator, and the tabs are re-titled on every live re-read. The panel's `iconPath` is one fixed icon on every mission tab, a built-in codicon through a `ThemeIcon`, so no image file and no light-theme variant is made for it.

- **Window of a mission that is no longer live.** A mission's window stays open when its mission stops being live. It replaces the mission's page with one fixed notice that the mission is no longer live, drawing no workflow diagram, recipe, pane, or action button, and the person closes it. If a later live read lists the path again, as after a reverted finish or a branch switched back, the window draws that mission's page again. The rule has no tie to the run bookkeeping.

### Activity-bar icon

- **Three arms of the icon.** The icon's two side arms are short arms cut verbatim from `assets/banner.txt` as a mirrored pair curling inward, a short arm from the drawing's left half on the left and one from its right half on the right. The centre arm is none of the banner's eight: it is a new arm drawn by hand in the banner's characters and style at a larger character scale, with more rows and columns than the banner's ten-row long arm. The script composes the three arms at one common character scale, so the centre is larger by its own drawing and no arm is magnified. The centre arm's drawing is therefore a second hand-drawn source of the icon beside the banner's drawing.

### Design drafts under `ideas/`

- **Follow-up record removed with the draft.** `ideas/vscode_extension_follow_up.md` is removed by this mission alongside `ideas/vscode_extension.md`, so no document is left holding references to the draft and none of its citations is rewritten. Its record of deferred work (the drift-gate guards, the tests left out, the Codex print check, publication, shipped Codex recipes) then stands only in git history.

### Side-bar view

- **Mission row layout.** A mission's row in the side-bar tree is a leaf with no child rows, one row per mission, so a click on the row stays free to open the mission's window. The label carries the mission's title. The description carries the next workflow step's name followed by both counts in a compact form, for example "Derive tasks · 3 questions · 2 tasks". The icon carries the running marker, a spinning `ThemeIcon` while the mission's run is going and a steady mission icon otherwise. The tooltip repeats all five facts spelled out in full beside the mission's path, giving whatever a narrow side bar cuts from the description.

- **Controls that belong to no mission.** Refresh and Settings are icon actions in the view's title bar. New mission and Define mission are two tree rows standing above the mission rows, each labelled with its control's name, its `description` showing the harness, model, and effort of the remembered variant. Clicking the row runs that variant, so a run still starts in one click with its variant shown before the click. An inline icon action on the row, also offered in its context menu, opens a QuickPick of the recipe's variants that changes the remembered selection without starting a run.

- **View with no mission to list.** Both states in which the view has no mission row to draw are shown through the tree view's own `message` property (`TreeView.message`), with the tree returning no mission row. With no mission live the message is today's line `No mission is live.`. When the live read fails it is today's failure line `The live missions could not be read.` followed by the cause as the read gave it. A successful read with missions clears the message. Nothing is added to the manifest for either state, with no welcome content, context key, or placeholder row, and the view's other contents, its title-bar controls included, stay as they are in every state.

### Commands

- **Command Palette commands.** The two existing command ids, `gurita.openMissionPane` and `gurita.refreshMissionPane`, are removed. The Command Palette offers one command of the extension's own beside the focus command VS Code generates for the view: a refresh command under a new id, with a title naming missions rather than the pane (such as Gurita: Refresh Missions). It re-reads the side-bar tree and every open mission and Settings window exactly as the side-bar's Refresh control does, and that control runs the same registered command. The commands behind New mission, Define mission, Settings, and opening a mission are hidden from the Command Palette through `menus.commandPalette` entries whose `when` is `false`.
