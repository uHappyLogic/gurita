# VS Code extension follow-up

A record, written 2026-11-20, of what the first version of Gurita for VS Code (`gurita-vscode`) leaves out, kept as potential follow-up work for later missions. The first version was built by the mission `gurita-vscode/mission_vs-code-extension-first-version/` from the design in `ideas/vscode_extension.md`, whose decisions stand for what the person sees and clicks. That mission's goal let it leave out the parts that only guard a long-lived extension and asked for everything left out to be written down; this document is that record. Each item below is a section of its own, grouped by kind: the guards a long-lived extension would want, the checks left unmade, and the product work deferred. Nothing here is decided or scheduled.

## Guards of a long-lived extension

The draft assigns four guards to the drift-gate workflow, `.github/workflows/drift-gate.yml`: the extension's build and tests, a check of its fixed lines against the table, a check of its parse against the open-question tool's filters, and a check that no snippet heading repeats. The first version carries out none of them. The workflow keeps its five steps unchanged (checkout, `astral-sh/setup-uv`, `uv run scripts/build_hosts.py --check`, and the two pytest runs), with no Node set up. The runner's pytest tests under `gurita-vscode/runner_tests/` are the one part of the extension CI runs, because `pyproject.toml`'s `testpaths` collects that directory in both pytest runs.

### The extension's Node steps in the drift-gate workflow

The extension's build (`npm ci`, `npm run compile`) and its TypeScript unit tests (`npm test`, Node's built-in `node:test` over the compiled files) run only by hand, under Node 22 through nvm, as `gurita-vscode/README.md` describes. A later mission could add a Node setup and those steps to the one drift-gate job, so that a change that breaks the extension's compile or its tests fails CI in the same commit. It would bring the second toolchain the draft's "What it costs" names into this repository's CI, with one more action pinned to a SHA and bumped by hand, and it would need the steps to run from `gurita-vscode/` in the one job rather than a matrix.

### The fixed-line cross-check against the table

The package carries the plugin's fixed lines as `bundled/fixed_lines.tsv`, written at package time by `gurita-vscode/scripts/bundle.js` from the `## Fixed console lines` table of `docs/skill-reference.md`, one `kind<TAB>line` row per table line. Since every line of the table is carried and the file is regenerated by every package, the copy cannot drift from the checkout it was built from, but nothing checks that the lines the extension relies on by name are still in the table: the loop's `Task completed.`, which alone takes a looped run to its next task. A plugin change that rewords that line would leave every looped run stopping after its first task with no test failing. The check the draft names would fail CI when a line the extension or runner holds as a literal is missing from the table or has changed kind.

### The parse cross-check against the open-question tool's filters

The extension parses `open_questions.xml` in process with a parser of its own (`gurita-vscode/src/questions.ts`), written against the format the open-question tool's module docstring states, and builds the question view from it. Its unit tests run it against the repository's committed fixtures and fixtures of its own, but nothing compares the blocks it selects with the blocks `core/tools/open_questions.py list --without-alternatives` and `list --without-recommendation` print over the same documents. The draft's check would run both over the committed question documents or fixtures and fail when they disagree, so a plugin change that moves the filters' meaning or the document format fails in the same commit rather than showing as a wrong or missing row. As the draft says, such a check covers only which blocks the parse selects, not how it reads the rest of a block.

### The snippet heading-repeat check

The recipe reader identifies a recipe by its `###` heading alone, so a button's fixed name and a rule's single-task line name each mean exactly one recipe only while every heading of `snippets/GURITA_USAGE.md` is unique. The first version made them unique by hand, the six repeated Antigravity headings gaining "(Antigravity)", but no test checks it, so a later edit that repeats a heading would make one recipe shadow another without a failure. The draft's check would fail CI on any `###` heading under `## Claude Code` and `## Antigravity` that repeats.

### Tests left out

Beyond the four guards, the first version's tests stop short in these places, each by the mission's decision on what its tests cover:

- **Nothing runs inside an editor.** The modules that import `vscode` (`src/extension.ts`, `src/pane.ts`, `src/runs.ts`) and the webview page's script (`src/webview/page.ts`) have no tests; only the modules importing nothing from `vscode` (the recipe reader, the question parser, the task heading read, and the other pure modules) are unit-tested. Opening the pane, its tabs and question rows, its buttons and input boxes, the refresh on file events, and the run terminals' lifecycle are checked only by hand. A later mission could add tests run under `@vscode/test-electron` or `@vscode/test-cli` in an editor instance.
- **No runner test starts a shell session.** The runner's tests cover its decisions (the preview print, rule matching and the default, line-kind inference, and the fixed-line verdict) and refuse `subprocess.Popen` outright, so the composed session script, the interactive `$SHELL` start and its `/bin/sh` fallback, the `tee` of each headless line into the run directory, the check step that ends the shell on a stopping line, and the closing keypress wait run untested. A test could run `runner.py chain` and `runner.py loop` against a stub host command printing chosen fixed lines.
- **The bundled copies are not compared with their sources.** `scripts/bundle.js` copies `core/tools/missions.py` and `snippets/GURITA_USAGE.md` verbatim and parses the fixed-line table, and no test checks the copies, the table parse, or the refusals the build step makes on a malformed table row. Since nothing copied is committed, the copies are as fresh as the last package; a test of the table parse would catch a change to the table's layout before a package is built from it.

## Checks left unmade

### What a Codex line's plain print opens with

Checked on this machine on 2026-11-22, with `codex` 0.159.3 and the plugin installed at 1.9.0 from this repository's `hosts/codex/plugins/gurita`. The runner reads every headless line by one rule for all hosts: its print, the line's standard output passed through `tee` into a run-local file, is read for its last success, no-op, or stop line of the bundled fixed lines, and a success or no-op line continues the chain while anything else stops it. The line run, from the project root with Codex's default sandbox and no flag, was `codex exec '$gurita:finish-mission'`, whose skill, given no `--mission`, stops with nothing changed on the fixed line `No mission resolved — pass --mission with a live mission's path.`. It exited 0, and its plain print on standard output opened with that fixed line: the print was the skill's final message alone, the fixed line and below it the missions tool's one `live` line, with nothing above it. Everything else Codex printed went to standard error: a `Reading additional input from stdin...` line (standard input was not a terminal), the `OpenAI Codex v0.159.3` banner, the session header between `--------` lines (workdir, model, provider, approval, sandbox, reasoning effort, session id), the transcript of the prompt, the agent's interim messages, and each command it ran with its output, the final message again under a `codex` line, and a closing `tokens used` count. Since the runner's `tee` takes standard output only, the file a check step reads holds the final message alone, the banner and header reaching the terminal only; `runner.py check` run over that print read the stop line and stopped, as a stop line should. A Codex line's plain print therefore opens with the skill's fixed line, the one rule reads Codex lines as it reads the other hosts', and the runner stays as it is.

## Deferred product work

### Publication

The extension is published nowhere while it is an experiment: it is packaged as a VSIX into `gurita-vscode/dist/gurita-vscode.vsix` and installed by hand with `code --install-extension`, and anyone else builds it from source. Its manifest names the publisher `uhappylogic`, but no Marketplace or Open VSX publisher was created, looked up, or reserved. Whether and where to publish is deferred, not ruled out, to be decided once the experiment is judged. A publication reserves the publisher id and the name `gurita-vscode` for good, and two facts that decision weighs were never checked: whether a published extension's name can be changed in place, and how publication outside the Marketplace, on a registry the VS Code forks read such as Open VSX, works. A release path for the extension would also be new: `scripts/set_version.py` and `/release-plugin` do not touch it, and its version, `0.1.0`, is bumped by hand.

### Shipped Codex recipes

The shipped recipe file holds lines for Claude Code and Antigravity only, and Codex is left to the ways-of-using page's legend and a person's own recipe file. Shipping Codex chains, single-task lines, or button recipes waits on the Codex print check above, since a shipped line whose print the runner cannot read would stop every chain it heads.
