# VS Code extension

A draft, written 2026-11-17, for work not yet defined: a Visual Studio Code extension that puts a UX layer over the plugin. It replaces two pieces of hand work, copying command lines into a terminal and reading `open_questions.xml` as raw XML, with buttons and a rendered view. It runs the host CLIs' own command lines and writes no mission file itself, so everything it does can still be done by hand. The draft records the hand work it replaces, what was measured, the parts, how a line is run, what was checked of VS Code and when, what it costs, what is decided, and the questions the work decides. It uses today's vocabulary (Gurita, mission, `--mission`), the plugin's since the rename `ideas/gurita.md` records, and names the extension Gurita for VS Code, its slug `gurita-vscode` (see The name).

## The hand work

A mission is driven today from a snippet file, the tracked `snippets/GURITA_USAGE.md`, titled "Gurita CLI usage snippets", that holds every command line the person runs. It holds two placeholders: `<mission_path>`, the mission's repo-relative path, and, on its two single-task lines, `<Task Title>`. Under a heading for each of Claude Code and Antigravity, and none for Codex, it holds one named, fenced block per situation: a first run (starting state, review, alternatives, recommendation), a requirements iteration (sweep, review, alternatives, recommendation), three execution blocks (normal, critical at a higher effort, and one with a further requirements pass first), a single task, and the finish. Beside them stand, under each heading, the bare slash commands of the conversational and single-question skills (on Claude Code `complete-task`'s as well), and, under Claude Code, two shell steps of the person's own: sourcing an environment file to switch to API-key usage, and waiting for the account's usage window to reset. The Antigravity heading also holds an install block, whose install line names a placeholder clone path, a mixed-host requirements review, an `agy models` line, and a `git log` one-liner that lists every mission in the project chronologically.

Per mission the person replaces `<mission_path>` throughout the file, then for each step copies a block and pastes it into a terminal, typing the task's title in place of `<Task Title>` on a single-task line. For a single-question skill they read the Short Title out of the XML, and for `answer-open-question-with-alternative` the alternative's id as well, and type both after the slash command.

Three properties of the file shape the design:

- **Hosts, models, and efforts are per line and personal.** A block mixes hosts: the critical execution block under Antigravity runs its last line on Claude Code, because the models `agy` runs there stop at `high`. Each line names its own model and effort, and `docs/ways-of-using.md` publishes other values for the same chains.
- **A block may end on an interactive line.** Where the recommendation line or the `complete-all-tasks` line closes a block it is written without `-p` (`agy -i` on Antigravity), so the session stays open and the person is in it when the run ends.
- **A stopped line does not stop a block.** The lines are joined by `;` and no skill sets an exit code, so a block runs every line after one that stopped.

The file has the form `docs/ways-of-using.md` already has: a heading naming the goal and one fenced block whose every line is a complete invocation, with the text to substitute in angle brackets. The page uses six placeholders: `<goal>`, `<scope>`, `<path>`, `<Short Title>`, `<Alternative Id>`, and `<answer text>`.

## Why an extension

Given by the maintainer on 2026-11-19, in that day's conversation with a collaborator about the snippet file and what the extension would do with it: the first reason in answer to the collaborator asking what command lines run in a terminal gain over workflows or commands inside Claude Code, the other two in saying why the layer is a VS Code extension.

- **A host gives two usable layers, an agent and its subagents.** It was said of Claude Code: an agent can call a subagent, and a subagent of a subagent can be had too, but it works differently, strangely, and going that deep, to a third layer, met many issues. So what orders the skills sits outside the host. The snippet file is that orchestrator today: it is the first layer, a Gurita skill called through the host's CLI the second, and an agent the skill dispatches, such as `complete-task`, the third. The maintainer called the limit one to work around, and the extension makes the workaround a button: the four lines of a first run become one click.
- **VS Code supplies what an application of its own would have to build.** A standalone application sounds like a good idea, but it would have to implement much itself, where VS Code works out of the box: its Git and GitHub integration, the changes view among it, although with Gurita taking care of so much the changes are seldom checked, and its integration with the terminal, the part called very important. Calling Gurita from an application of the maintainer's own, tried before, meant building the whole application-to-terminal communication, a great deal of work VS Code already does.
- **The extension is an experiment.** VS Code is the editor the maintainer works in, used now as a reader of text rather than of code, since working with Gurita is mostly reading text, so the extension extends that environment a little to try the visual flow, a choice the maintainer allowed suits them and not everybody. If it works, a deeper integration with the host may follow, with Claude Code or the Claude Code extension for VS Code, or a custom application of the kind the reason above weighs.

## What was measured

Read from this repository's history on 2026-11-17.

- **The question document is large when it is read.** Taking the largest committed version of `open_questions.xml` in each of the 13 most recent missions that held questions (`milestone_46` through `rename-milestone-to-mission`, directories named before the word's rename), the document held 9 to 41 questions in 56 to 329 KB. Ten of the thirteen held 12 to 18 questions in 90 to 137 KB. That is 6 to 8 KB a question.
- **It is hard to read as it stands.** The prose is entity-escaped (`&apos;`, `&quot;`, `&lt;`), a block's `<recommendation>` stands above its alternatives and names its option only by id, and a dependency is a bare `<depends-on question option/>` tag.
- **Most answers are accepted recommendations.** Counted by commit subject over the whole history: 622 `Recommendation-answer:`, 25 `Alternative-answer:`, and 32 `Manual-answer:`. So 57 of 679 answers (8%) were made by hand, and the person's sitting is mostly reading the whole set to find the few to override.
- **The list of live missions is short.** Two missions are live today and `missions.py live` prints them in two lines. A list alone is not worth an extension.
- **Every run's outcome is already a listed line.** The `## Fixed console lines` table of `docs/skill-reference.md` lists 94 lines (17 success, 27 no-op, 49 stop, and the one convergence verdict), and `tests/test_fixed_console_lines.py` checks each against every rendered host tree. CLAUDE.md gives the reason for the convention: a harness running the skills one invocation after another knows how each ended only from its final message.

## The constraint

The extension runs the command lines a person would type, through the host's own CLI, and writes nothing under a mission directory. Four things follow.

- **Manual use is unchanged.** A run started by a button is the run the pasted line starts. A person without the extension loses nothing, and a button can show the lines it is about to run.
- **The plugin changes nothing for it.** No new tool, subcommand, output form, or exit code is needed: the question view is drawn from the extension's own parse of `open_questions.xml`, with no plugin tool called (see Question view). Nor is one needed to run a chain: the runner is a file of the extension's own, bundled in its package and found by its own path, so the plugin gains no tool for it (see Running a line).
- **It could record nothing on its own anyway.** Every recording step is a model run: the answer core judges what an answer supersedes and which picks it undermines. The open-question tool and the task-list tool stay the only writers of their files.
- **It reads two files and runs one read-only query to display them.** `open_questions.xml` whole, parsed in process (the open-question tool is that document's only writer, not its sole reader), and the `##` headings of `TASKS_TODO.md`; the live missions, with each one's path, title, and `started` or `defined`, come from the `live` query of the copy of `missions.py` the extension ships (see Mission pane).

## The parts

### Mission pane

One pane in the editor area, the one webview panel the extension keeps (see What was checked of VS Code), holds one page per live mission, and a way on the pane itself moves between missions. Each page names its mission by path and title and shows that mission's state, its open questions in the question view, its remaining task headings, and every button, the recipe buttons, which take their `<path>` from the page they stand on, and the per-question ones alike. Only the two buttons that start a mission, which belong to no mission and take no `<path>`, stand on the pane itself instead, beside the way between missions, so they are there when no mission is live (see Recipes). As a list of missions the pane adds little to `missions.py live`; its use is as the one surface the buttons hang on. It replaces both a side-bar tree of missions and a custom editor for the question document: the extension contributes no tree and claims no file, so `open_questions.xml` opened from the explorer shows its XML text, and one surface carries everything the tree and the editor were for, the least to build for an experiment.

- **The page's label.** A page shows its mission's state as a label built only from what the documents hold now: `started` or `defined`, whether any question lacks alternatives or a pick, whether the question list is empty, and whether tasks remain, read from the `##` headings of `TASKS_TODO.md`. It reads no run's output and no commit subject, so every fact is re-read from the project on each refresh, the extension keeps no memory of its own runs, and the finer states `ideas/kepala.md` names are not told apart. The label gates no button: every recipe button stays offered whatever the label reads, and the skills' own stop lines stay the only gate.
- **The question facts.** Whether any question lacks alternatives or a pick, and whether the question list is empty, come from the extension's own in-process parse of `open_questions.xml`, the one read the question view already makes, so the label and the view cannot disagree on a block and a refresh starts no process. The extension's tests, run as steps of the drift-gate workflow, run this repository's own `core/tools/open_questions.py list --without-alternatives` and `--without-recommendation` over the committed question documents or fixtures and fail when the parse selects different blocks, so a plugin change that moves the filters' meaning fails in the same commit.
- **`started` or `defined`.** The live missions, each with its path, title, and `started` or `defined`, come from the `live` query of a byte-identical copy of `missions.py` shipped inside the extension, found by the extension's own path and run with `python3`; no installed plugin is looked up. The copy is pinned to the plugin version the extension is built against, so the state comes from the plugin's own tested definition of the discovery pattern and the started test, with no per-host install lookup and no setup step.

### Recipes

A recipe is a name and a flat, ordered list of literal command lines with placeholders, run once per click from its first line to its last. The recipe format has no repeat construct and a button no repeat option: a further requirements iteration is the person clicking the same recipe again after reading how the last run ended, which the extension shows. The extension holds no model name, effort level, host flag, or skill order of its own: all of that is text in the lines.

- **Shipped recipes** are the blocks of the snippet file, `snippets/GURITA_USAGE.md`: each `###` heading under its `## Claude Code` or `## Antigravity` heading, with that heading's fenced block, is one recipe, identified by its heading alone, since every `###` heading is unique across the file. The pane offers every shipped recipe grouped under those two host headings, which are display grouping only. `docs/ways-of-using.md` stays separately written, neither generated from the snippet file nor checked against it.
- **Two hosts' lines ship.** Every chain is written out by hand under each of Claude Code and Antigravity, each line carrying that host's own model and effort, which is the snippet file as it stands, so nothing is written for it, and the mixed-host chain stays as written. Codex gets no shipped lines and is left to the ways-of-using page's legend for moving a line to another host and to a person's own recipe file.
- **What the snippet file still needs as a shipped document is a step of the work, not made here.** Its `<mission_path>` placeholder becomes `<path>`, the ways-of-using page's name for it. Its two personal blocks, `source .env_anthropic` under "API KEY usage" and `claude-wait` under "Wait for next quota reset", leave it, so the shipped file keeps no personal line. Each `###` heading that repeats under the other host names its host, for example "First run (Antigravity)", and a check that no heading repeats joins the extension's tests in the drift-gate workflow. And the five blocks that are not chains of host command lines, the two lists of bare slash commands, the Antigravity install block, the `agy models` line, and the `git log` one-liner listing every mission, move under one reference heading of their own (for example `## Reference`), standing apart from the host headings. The reader takes as recipes only the `###` blocks under `## Claude Code` and `## Antigravity` and never reads the reference section, which holds lines for hand use only, so the file stays the one usage reference a person reads by hand and no block that cannot run is offered as a button.
- **A person's own recipes** are one per-user file outside the project, serving every project, at a default path that a VS Code user setting changes, so the lines carrying a person's own hosts, models, and efforts stand in no tree, to be ignored or committed by accident. It is a flat list of `###` recipes in the same form: one carrying a shipped recipe's heading replaces that recipe, and any other is added to the shipped set. A shell step of the person's own is an ordinary line of such a recipe, a variant of a shipped chain, for example an "Execute tasks of normal difficulty (API key)" opening with `source .env_anthropic`, or one opening with `claude-wait;`. The step runs because it stands ahead of the chain's lines in the same recipe, and so in the same shell session, and it may stand mid-chain too, before a second `complete-all-tasks` line; the recipe format gains nothing for it and the extension gives no line handling of its own, at the cost of one copied chain for each variant a person runs.
- **The shipped file gains a recipe for each button outside the chains.** Like the changes above, this is a step of the work, the file unchanged here. It gains six entries of its own beside its blocks, each a `###` recipe under a fixed name, the names left to the work, standing under a host heading as every recipe does and holding one complete line, written out literally with its host binary, model, and effort as the file's other lines are and in the ways-of-using page's placeholder names. Two are interactive, in the interactive form (`claude "…"` with no `-p`, `agy -i "…"` on Antigravity): a `discuss-open-question --mission <path> <Short Title>` line and a `discuss-mission-goal <goal>` line. Four are headless: `answer-open-question-with-alternative --mission <path> <Short Title>. <Alternative Id>`, `answer-open-question --mission <path> <Short Title>. <answer text>`, `answer-open-question-with-recommendation --mission <path> <Short Title>`, and `define-mission-goal --at <scope> <goal>`, the define line a one-line recipe of its own, not the head of a chain. Each button runs the shipped recipe of its fixed name, the extension filling its placeholders and handing an interactive line to a terminal, and a person's own recipe of the same name replaces the shipped one, as for every other recipe. Every button's line thus comes from the one shipped source by the one reading rule: the buttons work with no recipe file of the person's own, the extension composes no line and holds no host flag, model, or effort, and `docs/ways-of-using.md` stays as it is, holding headless lines only.
- **Two buttons start a mission.** They stand on the pane itself, outside every mission's page (see Mission pane). The new-mission button asks for the goal in an input box and runs the shipped `discuss-mission-goal <goal>` recipe, opening a terminal on an interactive `discuss-mission-goal` session with that goal as the skill's text, where the person carries the conversation on to its proposed goal and `--at` scope and runs `/define-mission-goal` from inside the session. Beside it, for a goal that is already crisp, the define button takes the goal and the scope in input boxes and runs the shipped `define-mission-goal --at <scope> <goal>` recipe headless. So a mission is started in two ways, by conversation or by its one definition line.
- **The interface fills the placeholders.** `<path>` comes from the mission whose page the button stands on, `<Short Title>` and `<Alternative Id>` from the question and alternative clicked in the question view, and `<goal>`, `<scope>`, and `<answer text>` from an input box.

The shipped chains hold no per-question line: each per-question line is a one-line recipe of its own, run by its button in the question view. A chain that does hold one, as the ways-of-using page's "Answering the questions that matter to you" does, is not one button. It splits at the person's sitting: the question view records the hand answers one run at a time, through those one-line recipes, and a recipe button runs the lines after them, the shipped "Requirements iteration" recipe or an execution recipe, each opening on the sweep.

### Question view

A read-only view of one mission's `open_questions.xml`, shown on that mission's page of the pane. The extension reads the file itself, in process, with an XML parser of its own written against the document format the open-question tool's module docstring states, and builds the view and its buttons from what it parses. The plugin is unchanged for it, with no new subcommand, output form, or tool, and no plugin tool is called to draw the view.

Each question shows collapsed by default, as one row holding its Short Title and the id of its picked alternative, no pick being shown when the question carries none, so the set is screened by heading and only the questions that need it are opened. Opening a row shows the question whole, everything its block holds: the question text, the pick and its rationale against the alternative it names, every alternative with its what-it-is, advantage, and drawback, each dependency as a link to the sibling and the option it assumes, and the principles applied. The view carries expand-all and collapse-all controls, and the buttons no snippet file can, because the title and the id they fill come from the document, while each button's line comes from a shipped recipe of a fixed name (see Recipes):

- on a question's row, discuss it (the shipped interactive `discuss-open-question --mission <path> <Short Title>` recipe, handed to a terminal), answer it in the person's own words from an input box (the shipped `answer-open-question --mission <path> <Short Title>. <answer text>` recipe), or record its recommendation (the shipped `answer-open-question-with-recommendation --mission <path> <Short Title>` recipe), so a question is discussed or answered without being opened;
- on an alternative, inside the opened row, record it (the shipped `answer-open-question-with-alternative --mission <path> <Short Title>. <Alternative Id>` recipe);
- on the document, record every remaining recommendation, the sweep, through the shipped recipes that open on its line, "Requirements iteration" and the execution recipes, since no shipped recipe runs it alone (see Recipes).

The view re-reads the file after every run, since an answer removes its block and may clear the picks on other questions, and that redraw costs the one file read, with no process started.

## Running a line

- **Where a chain runs.** Every chain a button starts runs under the runner, one stdlib-only Python file (Python 3.9+, no `uv`, no third-party package) bundled in the extension's own package. The extension starts it as a terminal's own process through `TerminalOptions.shellPath` and `shellArgs`: `python3`, with the file's path under the extension's install directory and the chain's lines as an argument list, with `isTransient` set; a task's `ProcessExecution` gives the same process. The extension finds the file by its own path, so the plugin gains nothing and no installed plugin location is looked up. The runner starts each line of the chain itself, reads each headless line's output through a pipe, and decides whether to go on. So the run stays in view in a real terminal while stopping a chain rests on nothing a person's shell setup can switch off, with no shell integration involved, and the chain logic stands in one plain script a person can start by hand outside the editor, needing only the `python3` the plugin already requires.
- **One shell session per chain.** The runner runs a chain's lines in one shell session started for that run, so a recipe's shell step of the person's own, sourcing an environment file or calling a shell function such as the snippet file's `claude-wait`, takes effect for every line after it.
- **What kind a line is.** The recipe form carries one mark the shell ignores, and only an interactive line carries it: a trailing `# interactive` comment. The runner infers the rest. A marked line is started with the terminal inherited and is not read. An unmarked line holding a `gurita:` skill invocation, written `/gurita:` or `$gurita:`, is headless: its output is piped to the runner and its final message's first line read. Every other unmarked line is a shell step, run in the chain's shell session and not read, the chain going on after it. A headless last line is therefore still read, as the blocks that close on one need. An interactive line holds a `gurita:` invocation too, so the interactive lines that close the snippet file's blocks gain the mark, a step of the work beside those the Recipes part names, while its shell steps and headless lines stay as written. An interactive line prints no final message to read, so a chain ends on one, as the snippet file's blocks do.
- **Stopping a chain.** The runner runs each headless line exactly as the recipe writes it, with no output flag added, and reads only the run's plain print: the first line of the final message is looked up in the `## Fixed console lines` table of `docs/skill-reference.md`. A success or no-op line continues the chain, and a stop line, or any line the table does not hold, stops it, which the `;` in the snippet file cannot do. The process's exit code is not read, and nothing tells a host-level failure apart from an unlisted line, both stopping the chain. What Codex's plain print opens with stays to be checked (see Questions for the work).
- **Quoting.** A Short Title or a typed answer lands inside the line's quoted prompt. The ways-of-using page asks the person to write no double quote there (no single quote on a Codex line), and `ideas/short_title_characters.md` records the same failure for titles. So a substituted value, `<path>`, `<Short Title>`, `<Alternative Id>`, `<goal>`, `<scope>`, or `<answer text>`, never enters the line's text. The extension puts every value in the chain's shell session's environment when it starts the session, all of a chain's values being fixed when its button is clicked, and writes the placeholder into the line as a reference to that variable suited to the placeholder's quoting: as is inside a double-quoted prompt, and on a Codex line by closing and reopening the single quotes around it. The shell expands the reference without parsing what the value holds, so no character is refused or escaped, and a value typed into an input box may hold any character.
- **How long a run lives.** No longer than the editor, by decision (see Decided). The runner's terminal is marked transient, so a restart never starts a chain again, and a runner that is ended ends the line it is running, so nothing a button started keeps running unseen.
- **Permission flags.** `--dangerously-skip-permissions` and its Codex counterpart are text in a recipe line. The extension never adds one.
- **Runs side by side.** Two missions' chains may run at once: every commit takes its own paths as its pathspec, a git write outlasts another run's lock, and the scope gate holds a second mission in an overlapping scope at task entry. Within one mission the extension runs one chain at a time.

## What was checked of VS Code

Read from the VS Code documentation on 2026-11-17 (pages under Sources).

- **A custom editor can claim the question document.** A `customEditors` contribution selects files by a `filenamePattern` glob, which may match on directory names (the guide's example is `**/translations/*.json`). Priority `default` uses the custom editor for every matching file and `option` leaves it for the person to switch to. `CustomReadonlyEditorProvider` is the type for an editor that does not edit.
- **A publisher id is permanent and a removed name is gone.** The publisher's "ID cannot be changed once created", and after an extension is removed "its extension name is permanently reserved and cannot be reused, even by the original publisher". An extension can be deprecated in favour of another, which shows a Migrate button, but "VS Code will not automatically migrate or uninstall already installed deprecated extensions". Whether a published extension's name can be changed in place is not stated on the page.
- **A terminal's process survives a window reload, not a restart.** On reload VS Code reconnects to the previous process. On a restart "a terminal's content is restored and the process is relaunched using its original environment", so a command that was running is not continued.
- **An extension can run a command in a terminal, read what it prints, and learn when it ended, where shell integration is active.** The 1.93 release notes say "The terminal shell integration API is now available to use" and show `shellIntegration.executeCommand(...)` and `window.onDidEndTerminalShellExecution`, whose event carries `exitCode`. `TerminalShellExecution.read()` gives "a stream of raw data (including escape sequences) that is written to the terminal", holding only what was written after its first call. `executeCommand` takes a command line, or an executable with a list of arguments, whose escaping covers an argument that "contains whitespace and does not include any single quote, double quote or backtick characters" and "is not intended to be a security measure". The call "is not guaranteed to work as shell integration must be activated", and `Terminal.shellIntegration` "may remain undefined if shell integration never activates", a person's shell setup being one named cause. Without it the fallback is `sendText`, and then "we can't know when the command has finished or what the exit code was". Shell integration activates by itself for bash, fish, pwsh, and zsh on Linux and macOS and for Git Bash and pwsh on Windows, and not in a sub-shell, a plain `ssh` session, or "some complex shell setups".
- **An extension can start a process of its own as a terminal.** `TerminalOptions` takes `shellPath` and `shellArgs`, a list, so the process gets its arguments unparsed by any shell. `isTransient` opts the terminal out of the persistence that would otherwise relaunch the process on a restart. `Terminal.exitStatus.code`, read in `window.onDidCloseTerminal`, is the process's exit code. A task does the same and keeps its terminal: `ProcessExecution` takes a process and a list of arguments, `tasks.onDidEndTaskProcess` carries the process's `exitCode`, and the presentation option `close` "controls whether the terminal is closed after executing the task". A `Pseudoterminal` is the third form, a terminal whose content the extension writes itself.

The output read and the argument-list form were left unconfirmed by the first check, the API reference page being too long for it, and were then read from the API definitions the installed VS Code ships (1.143.0, `out/vscode-dts/vscode.d.ts`), as the last bullet's facts were. The exit code alone does not tell how a skill ended, since no skill sets one, so stopping a chain rests on reading the output, whichever way a line runs.

Read from the VS Code documentation on 2026-11-19, for the pane the draft adopts, a webview panel in the editor area (pages under Sources), with every API fact below confirmed against the same installed definitions, 1.143.0's `out/vscode-dts/vscode.d.ts`.

- **A webview panel is a page the extension draws in the editor area.** `window.createWebviewPanel(viewType, title, showOptions, options)` creates and shows a new panel, `showOptions` being a `ViewColumn` or a `viewColumn` with an optional `preserveFocus`, and the guide says such panels "are shown in VS Code as distinct editors". `WebviewPanel.viewColumn` is the panel's editor position, a panel "may only show in a single column at a time", and `reveal(viewColumn?, preserveFocus?)` moves it to another. Its content is `webview.html`, which "should be a complete, valid html document", and changing it "causes the webview to be reloaded"; its `title` is the label shown in the UI.
- **One pane is the one panel the extension keeps.** Every call creates a new panel, so a single pane is the extension holding the panel it created: the guide's example keeps it, calls `reveal` when its command runs again, and drops it on `onDidDispose`, which fires when the person closes the panel or `dispose()` is called, using a disposed panel throwing an exception.
- **A button on the page reaches the extension as a message.** Scripts run only when `enableScripts` is set, which "Defaults to false". The page's script calls `acquireVsCodeApi()`, which "can only be invoked once", and posts through it a string or JSON-serializable object, which the extension receives on `webview.onDidReceiveMessage`; the extension's `webview.postMessage` goes the other way, delivered only to a live webview. A button therefore posts a message and the extension starts the terminal, as the 2026-11-17 bullets above describe.
- **A hidden pane loses its content and keeps a saved state.** A panel's "html context is created when the panel becomes visible and destroyed when it is hidden", in a background tab included, and a state the page saves with `acquireVsCodeApi().setState()` is read back through `getState()` when it becomes visible again. Whether that state outlives the extension setting `webview.html` anew, which reloads the page, neither source says. `retainContextWhenHidden` keeps the content of a hidden panel but "has a high memory overhead", and whether such a panel receives a message the sources do not agree: `postMessage` delivers to a webview "in the background with `retainContextWhenHidden`", as the guide also says, while the option's own comment reads "You cannot send messages to a hidden webview, even with `retainContextWhenHidden` enabled".
- **A pane outlives a restart only through a serializer.** A `WebviewPanelSerializer` registered with `window.registerWebviewPanelSerializer`, under an `"onWebviewPanel:viewType"` activation event, has the editor save its panels' `setState` state at shutdown and pass it to `deserializeWebviewPanel` after the restart, and the guide says serialization is "only enabled if your extension registers a `WebviewPanelSerializer`".
- **The page shows workspace content and must be guarded.** The definitions ask for "properly sanitizing all untrusted input (including content from the workspace) and setting a content security policy", whose origin is `webview.cspSource`, and the guide names "File contents" and "File and folder paths" among the values to sanitize, which is what the question view shows. `localResourceRoots` defaults to "the root folders of the current workspace plus the extension's install directory", an empty list allowing none.
- **Webviews are to be used sparingly.** The guide calls them "resource heavy", to be used "only when VS Code's native API is inadequate", and the UX guidelines say "Only use webviews when absolutely necessary". The pane is one webview, standing in for the tree and the custom editor rather than beside them.

Two surfaces still stand unchecked, and neither matters any longer: the side-bar tree, which the pane replaced, the extension contributing no tree, and the publication of an extension outside the Marketplace, since the extension is published to no registry while it is an experiment (see What waits).

## Kepala

The runner is the transition engine `ideas/kepala.md` outlines, with a person choosing the edge. Kepala runs the skills through the CLI, reads the coarse state from `missions.py live` and the fine state from the last fixed first line, and names the `Recommended` state as where the team comes in. The question view is that state's interface. So the recipes, the fixed-line reading, and the state read are kept apart from the VS Code interface, in a part with no dependency on it. Whether Kepala then uses that part is Kepala's question.

## The name

The extension takes a descriptive name, the plugin's name with a qualifier: its display name is Gurita for VS Code and its slug `gurita-vscode`. It coins no word, and Kepala and Kepalagurita stay what `ideas/kepala.md` gives them, the orchestrator's name and the name of the whole. Nothing is reserved under the name: while the extension is an experiment it is published nowhere (see What waits), so no publisher id or extension name is held for good before the experiment is judged.

Looked up on 2026-11-19, the exact slug directly on the two extension registries and on GitHub, the `gurita` stem having had its own direct lookup on 2026-11-10 (`ideas/gurita.md`), which covered no extension registry. Nothing holds the slug:

- **The Visual Studio Marketplace holds no `gurita-vscode`.** Its extension query, run for VS Code extensions, returned no result for `gurita-vscode` and none for `gurita`, so no extension's name or display name there carries the word.
- **Open VSX holds no `gurita-vscode`.** Its query by extension name returned no extension named `gurita-vscode` and none named `gurita`, in any namespace, and neither `gurita-vscode` nor `gurita` exists as a namespace. Its search for `gurita` returned one result, `danisss9.guito` (Guito), a near spelling, not the word.
- **GitHub holds no `gurita-vscode`.** A repository search for the slug in a name returned none, no account or organisation is named `gurita-vscode`, and of the 91 repositories with `gurita` in their name, the plugin's own four among them, none is an editor extension, the nearest being `yandyrohman/guritamarket-ext-release`, the releases of a browser extension named Gurita Market.

## What it costs

- **A second toolchain.** TypeScript, Node, and packaging, in this repository, in a directory outside `core/` that is rendered into no host tree, beside code that is otherwise stdlib-only Python, Markdown, and one build script. The extension's build and tests run as steps of the existing one-job drift-gate workflow (`.github/workflows/drift-gate.yml`), which puts that second toolchain into this repository's CI. Its release costs nothing while it is an experiment (see What waits).
- **A copy of the contract.** The extension relies on the recipes it ships and on fixed lines of the `## Fixed console lines` table of `docs/skill-reference.md`, both of which the plugin can change under it. Kept in this repository, both stand one checkout away, and one of the drift-gate workflow's steps checks the extension's fixed lines against the table, so a plugin change that moves a fixed line the extension relies on fails CI in the same commit instead of outrunning the extension. Since the plugin's rename every line of either that names the plugin carries `gurita`, so a copy made now starts from the new name.
- **Little reach.** The plugin has few users, so the first user is the maintainer. The case rests on the maintainer's own hand work, 57 finished missions and 679 recorded answers, not on new users.
- **A second reader of the question document.** The extension parses `open_questions.xml` with an XML parser of its own, written against the document format the open-question tool's module docstring states, so the open-question tool is no longer the document's only parser, and a change the plugin makes to the format is one the extension's parser must follow. The drift-gate step that checks the parse against the tool's `list --without-alternatives` and `--without-recommendation` (see Mission pane) checks only which blocks the parse selects, not how it reads the rest of a block.

## What waits

Nothing here is carried out yet, and nothing outside it is waited on. Both renames have landed, shipped together as the plugin's 2.0.0 release (`ideas/gurita.md`), so the extension starts under the new name, with recipes and fixed lines that already say mission. The namespace is data to the extension, as the flag and the discovery pattern are.

Publication waits on the experiment. While the extension is an experiment it is published to no registry and no release page: it is packaged from this repository as a VSIX and installed by hand into the maintainer's own editor, and anyone else who wants it builds it from source. Publishing to a registry is deferred, not ruled out, to be decided once the experiment is judged.

## Decided

Decided on 2026-11-17.

- **A run lives no longer than the editor.** Every run the extension starts ends when VS Code exits, abruptly if need be, and nothing is built to carry a run across a restart or to pick one up after it. An abrupt end is what closing the terminal under a pasted line already is, and the plugin already answers it: `complete-all-tasks` run again continues from the remaining tasks, each task being committed on its own and a stopped task's partial work continued; the answer sweep stops on its fixed line while a mission file holds an uncommitted change; and a git lock a killed process left surfaces as git's message.
- **No local server.** Nothing the extension does runs behind a listener. A server was considered only as a way around limits of the terminal API, and the check found none that needs one: an extension can start a process as a terminal or a task with an argument list and read its exit code, and where shell integration is active it can read what a command prints. A chain is run by the extension itself or by one process per chain that ends with it and keeps no state.

Decided on 2026-11-19.

- **The extension lives in this repository.** Its code stands in a directory outside `core/` that is rendered into no host tree, and its build and tests run as steps of the existing one-job drift-gate workflow, among them a check of the extension's fixed lines against the `## Fixed console lines` table of `docs/skill-reference.md`. A repository of its own was set aside: here the recipes and the fixed-line table stand one checkout away, and a plugin change that moves a fixed line the extension relies on fails CI in the same commit, where a separate repository would carry copies the plugin could outrun.
- **The extension is published nowhere while it is an experiment.** It goes to no registry and no release page: it is packaged as a VSIX and installed by hand, and anyone else who wants it builds it from source. No publisher account, token, or publish step joins the release of the three host trees, so no publisher id, which cannot be changed, and no extension name, which a removal does not free, is reserved for good before the experiment has proved out. Registry publication is deferred, not ruled out, to be decided once the experiment is judged.
- **The extension is named Gurita for VS Code, its slug `gurita-vscode`.** A descriptive name carrying the plugin's says the one thing that sets the extension apart from the plugin and the orchestrator, that it is Gurita's interface in VS Code. It coins no word, needs one narrow lookup, and leaves Kepala and Kepalagurita to what `ideas/kepala.md` gives them. The slug was looked up directly on the Visual Studio Marketplace, Open VSX, and GitHub on 2026-11-19 and found free (see The name), and since the extension is published nowhere while it is an experiment, the one lasting cost of the name, a published name that cannot be taken back, does not arise before the experiment is judged.
- **One pane in the editor area holds a page per live mission.** A way on the pane itself moves between missions, and each page shows that mission's state, its open questions, its remaining tasks, and every button, the per-question ones included. The pane replaces both the side-bar tree of missions and the custom editor: the extension contributes no tree and claims no file, so `open_questions.xml` opened from the explorer shows its XML text. One surface then carries everything the tree and the editor were for, the least to build for an experiment, and it rests on `window.createWebviewPanel`, which stands in the installed 1.143.0 API definitions.
- **The page's label tells apart only what the documents hold now, and gates no button.** It shows `started` or `defined`, whether any question lacks alternatives or a pick, whether the question list is empty, and whether tasks remain, and it reads no run's output and no commit subject, so every fact is re-read from the project on each refresh and the extension keeps no memory of its own runs, the finer states `ideas/kepala.md` names left untold. Every recipe button stays offered whatever the label reads, so the skills' own stop lines stay the only gate.
- **The page's question facts come from the extension's own parse of `open_questions.xml`, checked against the tool's filters.** It is the one read the question view already makes, so the label and the view cannot disagree on a block, a refresh starts no process, and nothing beyond `missions.py` is bundled. The extension's tests in the drift-gate workflow run `core/tools/open_questions.py list --without-alternatives` and `--without-recommendation` over the committed question documents or fixtures and fail when the parse selects different blocks, so a plugin change that moves the filters' meaning fails in the same commit.
- **`started` or `defined` comes from the `live` query of a byte-identical `missions.py` shipped inside the extension.** The copy is found by the extension's own path, run with `python3` for both the live list and the state, and pinned to the plugin version the extension is built against, so the state comes from the plugin's own tested definition of the discovery pattern and the started test, with no installed plugin looked up and no setup step. A glob of the discovery pattern was set aside, as a second copy of the pattern that cannot tell `started` from `defined`.
- **The extension reads `open_questions.xml` itself, with an XML parser of its own.** The parser runs in process, written against the document format the open-question tool's module docstring states, and the question view and its buttons are built from what it parses. The plugin is unchanged, with no new subcommand, output form, or tool, and no plugin tool is called to draw the view. The view then shows everything a block holds, the advantages, drawbacks, dependencies, and principles included, and a redraw after a run costs one file read with no process started. A render by a plugin tool, to Markdown or HTML that the view would show, was set aside: it would add a tool and an output form to the plugin and start a process on every redraw.
- **Each question shows collapsed by default to one row, its Short Title and the id of its picked alternative.** A question carrying no pick shows none. The question-level buttons, discuss, answer in the person's own words, and record the recommendation, stand on the row; opening the row shows the question whole, with the alternative buttons inside it, and the view carries expand-all and collapse-all controls. The maintainer screens most questions by their heading alone, as they said in the 2026-11-19 conversation, and the sitting is mostly reading the whole set to find the few to override (see What was measured), so a row per question lets the set be screened by heading and only those few opened, while a question can still be discussed or answered without being opened.
- **The shipped recipes are the `###` blocks of `snippets/GURITA_USAGE.md`, and `docs/ways-of-using.md` stays separately written.** Each recipe is a `###` heading under `## Claude Code` or `## Antigravity` with that heading's fenced block. The file's blocks already are the buttons the 2026-11-19 conversation describes, a first run, a requirements iteration, the execution variants, a single task, and the finish, it already carries the single-task line with `<Task Title>`, and it is the file the maintainer, the extension's first user, works from. The page parsed as it stands, the page reshaped to the buttons, and a data file the page is written from or checked against were set aside, so the page and the snippet file stay two hand-written copies, with no generation and no check between them.
- **The snippet file is described as it stands, and the work changes only what a shipped document needs.** Its title, "Gurita CLI usage snippets", and its install line, naming a placeholder clone path, already suit a shipped document, so the draft gives them as they are, a present-tense description corrected in place with nothing of the file's history added. What is left to the work is the placeholder, the personal blocks, the repeated headings, and the place of the non-chain blocks (see Recipes).
- **Every `###` heading of the snippet file is unique, and a recipe is identified by its heading alone.** Each heading that repeats under the other host names its host, for example "First run (Antigravity)", a check that no heading repeats joins the extension's tests in the drift-gate workflow, and the pane groups the recipes under the file's `##` host headings for display only. A button that runs a recipe by a fixed name, and a choice that names a single-task line, each need that name to mean exactly one recipe; one flat namespace gives it, the reading rule needing no second part, and lets a flat own recipe file replace exactly one shipped recipe.
- **The five non-chain blocks stay in the snippet file, under one reference heading the reader never reads.** The two lists of bare slash commands, the Antigravity install block, the `agy models` line, and the `git log` one-liner listing every mission move under a heading of their own (for example `## Reference`) apart from the host headings, and only the `###` blocks under `## Claude Code` and `## Antigravity` are recipes. The file stays the one usage reference a person reads by hand, as manual use being unchanged asks, and no block that cannot run is offered as a button, at the cost of one layout rule, that a `###` block is a recipe only under a host heading.
- **The two personal blocks leave the snippet file, and a shell step of a person's own is a line of their own recipe.** `source .env_anthropic` and `claude-wait` go, so the shipped file keeps no personal line, and a person who wants one in a run writes a variant of a shipped chain in their own recipe file, opening with the step or carrying it mid-chain, before a second `complete-all-tasks` line. A step is a line of the recipe it belongs to and takes effect for every line after it in the same shell session, so the recipe format gains no construct and the extension gives no line handling of its own, at the cost of one copied chain for each variant a person actually runs.
- **Command lines ship for two hosts, Claude Code and Antigravity, and Codex gets none.** Every chain is written by hand under each, with that host's own models and efforts, which is the snippet file as it stands, so nothing is written for it, and the mixed-host chain stays as written. A Codex heading would hold lines nobody runs while the extension is installed by hand into the maintainer's editor and what Codex's plain print opens with is still unchecked, so Codex is left to the ways-of-using page's legend and a person's own recipe file.
- **A person's own recipes are one per-user file outside the project.** It serves every project, at a default path a VS Code user setting changes, and it is a flat list of `###` recipes, one carrying a shipped recipe's heading replacing it and any other added. Its lines carry a person's own hosts, models, and efforts, which the draft finds personal, and the maintainer already drives every mission from one file of lines, so a per-user file fits, with nothing personal standing in any tree to ignore or commit by accident.
- **A recipe is a flat, ordered list run once per click, with no repeat construct.** The format has no repeat and the button no repeat option, and a further requirements iteration is the person clicking the same recipe again after reading how the last run ended, which the extension shows. The maintainer screens the questions between rounds and stops by judgment, after none, one, or rarely two iterations, never on convergence, so a repeat ending on the convergence line would run unscreened exactly the rounds the maintainer chooses to screen; a click per round keeps that pause and adds no ordering logic to the extension.
- **A new-mission button opens an interactive `discuss-mission-goal` session, beside the button for the headless definition line.** It asks for the goal in an input box and opens a terminal on an interactive `discuss-mission-goal` session with that goal as the skill's text, where the person carries the conversation on to its proposed goal and `--at` scope and runs `/define-mission-goal` from inside the session; the button for the headless `define-mission-goal --at <scope> <goal>` line, its goal and scope typed into input boxes, stays beside it for a goal that is already crisp, so the draft names two ways to start a mission. The maintainer starts a mission with `discuss-mission-goal`, which asks high-level questions and proposes a goal in a directory, and in the 2026-11-19 conversation described clicking for a new mission, writing the goal, and being redirected to the terminal to carry the conversation on there, which is this button; a goal that needs no conversation keeps its one headless line.
- **The interactive lines behind the buttons are entries of their own in the shipped snippet file, written out literally.** The `discuss-open-question --mission <path> <Short Title>` and `discuss-mission-goal <goal>` lines stand in `snippets/GURITA_USAGE.md` beside its blocks, in the interactive form (`claude "…"` with no `-p`, `agy -i "…"` on Antigravity), host binary, model, and effort included; the extension fills `<path>`, `<Short Title>`, and `<goal>` and hands the line to a terminal, and a person's own recipe of the same name replaces a shipped line. The buttons then work with no recipe file of the person's own, the extension still holds no host flag, model, or effort, and `docs/ways-of-using.md` stays as it is, holding headless lines only.
- **Each answer button and the define button run a one-line headless recipe of a fixed name that the shipped snippet file gains.** The file gains `answer-open-question-with-alternative --mission <path> <Short Title>. <Alternative Id>`, `answer-open-question --mission <path> <Short Title>. <answer text>`, `answer-open-question-with-recommendation --mission <path> <Short Title>`, and `define-mission-goal --at <scope> <goal>`, each a `###` recipe of its own written with its host binary, model, and effort as the file's other lines are and in the ways-of-using page's placeholder names, the define line a recipe of its own, not the head of a chain; each button runs the recipe of its fixed name, and a person's own recipe of the same name replaces it, as for every other recipe. Every button's line then comes from the one shipped source by the one reading rule, the extension composes no line and holds no host flag, model, or effort, and `docs/ways-of-using.md` is untouched.
- **A chain runs under a runner started as a terminal's own process.** The extension starts it through `TerminalOptions.shellPath` and `shellArgs`, an argument list, with `isTransient` set, or through a task's `ProcessExecution`, which gives the same process; the runner starts each headless line of the chain itself, reads its output through a pipe, and decides whether to go on, and an interactive last line inherits the terminal. The run then stays in view in a real terminal while stopping a chain rests on nothing a person's shell setup can switch off, and the chain logic lands in one part a person can start by hand outside the editor. Typing the line into the terminal and reading it through shell integration was set aside, as a raw stream with escape sequences that works only where the person's shell setup lets shell integration activate, and so was a child process of the extension, which needs neither but takes the run out of the terminal.
- **The runner is one stdlib-only Python file bundled in the extension.** Kept to Python 3.9+, with no `uv` and no third-party package, it is started by the extension as the terminal's process, `python3` with the file's path under the extension's install directory and the chain's lines as arguments, and found by the extension's own path. It needs only the `python3` the plugin already requires, where `uv`, this repository's development tool and named nowhere under `core/`, would add a prerequisite the plugin does not have; the plugin gains nothing and no installed plugin location is looked up, which a runner shipped as a plugin tool, set aside, would have brought back; and the runner stays a plain script a person can start by hand outside the editor.
- **A chain is one shell session, and every substituted value reaches its line through that session's environment.** The session is started for the run, so a recipe's shell step of the person's own, sourcing an environment file or calling a shell function such as the snippet file's `claude-wait`, takes effect for every line after it. A value (`<path>`, `<Short Title>`, `<Alternative Id>`, `<goal>`, `<scope>`, `<answer text>`) never enters the line's text: the extension puts it in the session's environment when it starts the session, all of a chain's values being fixed when its button is clicked, and writes the placeholder into the line as a variable reference suited to the placeholder's quoting, which the shell expands without parsing what the value holds. No character is refused or escaped, so a Short Title or an answer holding the quote the ways-of-using page asks a person to avoid runs as typed, and refusing or escaping such a value where the extension types into a shell, the 2026-11-17 draft's answer, was set aside.
- **An interactive line carries a trailing `# interactive` comment, and the runner infers every other line's kind.** A marked line is started with the terminal inherited and not read; an unmarked line holding a `gurita:` skill invocation, written `/gurita:` or `$gurita:`, is headless, its output piped and its final message's first line read against the fixed-line table; every other unmarked line is a shell step, run in the chain's shell session and not read, the chain going on after it. The mark is the one thing the recipe form gains, a comment the shell ignores, so a pasted line still runs as written; a headless last line is still read, as the blocks that close on one need; and the snippet file's shell steps and headless lines stay as written.
- **A headless line runs exactly as the recipe writes it, and only the first line of its final message is read.** No output flag is added, and that line of the run's plain print is looked up in the `## Fixed console lines` table of `docs/skill-reference.md`: a success or no-op line continues the chain, and a stop line, or any line the table does not hold, stops it. The process's exit code is not read, since no skill sets one, and nothing tells a host-level failure apart from an unlisted line, both stopping the chain. A run started by a button stays the run the pasted line starts, and the fixed lines are already how a harness running the skills one invocation after another knows how each ended; the structured output each host offers (`--output-format stream-json` on Claude Code and Antigravity, `--json` on Codex), which `host_tests/conftest.py` reads for all three, was set aside as a flag the pasted line does not carry. What Codex's plain print opens with stays to be checked.

## Questions for the work

- **What Codex's plain print opens with.** The runner looks up the first line of a headless run's final message, read from its plain print, in the fixed-line table (see Running a line). Whether a Codex line's plain print opens with that line was not checked, and no shipped line is Codex's (see Recipes); a Codex line in a person's own recipe file whose print opened with anything else would stop its chain as an unlisted line.
- **How the page is redrawn after a run.** The view re-reads the question document after every run, and a redraw that resets the page closes the rows the person opened unless it kept them. The documentation read on 2026-11-19 leaves unstated whether a state the page saved with `setState` outlives the extension setting `webview.html` anew, and it disagrees on whether a hidden panel kept with `retainContextWhenHidden` receives a message (see What was checked of VS Code), so whether the page is redrawn by a new `webview.html` or by a message to the visible page stays to be settled, against the installed editor.
