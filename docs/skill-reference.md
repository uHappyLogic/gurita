# Skill reference

What each of Gurita's skills does, in the order a mission uses them, and the one subagent you see dispatched. The phases the skills form, how they commit, and the [answer-principle-learning loop](workflow.md#the-answer-principle-learning-loop) are described in [workflow.md](workflow.md), and how to chain them as headless command lines is in [ways-of-using.md](ways-of-using.md). Each skill's own `SKILL.md` is its exact behaviour; this page says what it is for, when to run it, and what it leaves behind.

Every skill that works inside a mission takes the mission's path as a required leading `--mission <path>`, exactly as `/define-mission-goal` printed it, trailing slash included, for example `mission_user-guide/`. No mission is current, so several can stand at once and each run names the one it works on. A call that names no mission, or a path that matches none, stops with the live missions listed beneath, so you can retry with the right path. Below, the *context file* is the project's `CLAUDE.md` on Claude Code and its `AGENTS.md` on Antigravity and Codex.

### `init-mission-base-workflow`

Run once per project, before any other skill. It makes sure the context file carries the `## Mission Workflow` section, which tells anyone working in the project where missions live and how each is named and finished: it creates the file when it is missing, appends the section when it is absent, and leaves a file that already holds the section exactly as it is. In a project an earlier copy of the plugin bootstrapped, it replaces the older `## Milestone Workflow` section whole and, in the same pass, moves the principle store from `milestones/answer_decision_principles.md` to the project root, so run it once more after upgrading such a project. Changes already uncommitted in the context file, such as a file `/init` just wrote, ride in its one `Workflow-bootstrap: missions` commit. It checks no prerequisites and creates no mission.

### `discuss-mission-goal <overall_goal_description>`

A conversation that sharpens a vague goal before anything is created. It reads the context file and an overview of the project's record, one line per live or finished mission, reading deeper into the missions that bear on the goal; then it restates the goal and asks the few questions whose answers most change the scope. It ends by proposing a refined goal and the mission's placement: the one existing directory holding the core of the work, as deep in the tree as the core allows, and the root `.` only when the core is the project itself. Work the mission also needs elsewhere does not widen the placement, because a mission placed higher overlaps every mission beneath it, and overlapping missions execute one at a time. Once you confirm both, it suggests the `/define-mission-goal --at <scope> <refined goal>` line to run. Creates no files.

### `define-mission-goal --at <scope> <overall_goal_description>`

Creates a new mission. It first checks that the workspace lies inside a git work tree and that `python3` is Python 3.9 or later, stopping before it writes anything, with the remedy, when either is missing; it never runs `git init` itself. It then chooses a title from your goal and creates `<scope>/mission_<slug>/` directly in the directory `--at` names, `.` for the root, holding `requirements.md` headed by the title with its Goal filled in, an empty `open_questions.xml`, and an empty `TASKS_TODO.md`. The directory is named by a slug of the title, with no number. `--at` has no default, and the scope must be an existing directory inside the workspace, written as a relative path with no whitespace or shell-syntax characters; the same title twice in one scope is refused. It commits under `Mission-definition: <path>` and prints the mission's path, which every later skill takes as its `--mission <path>`. Defining a mission activates nothing.

### `specify-mission-starting-state --mission <path>`

Fills the `## Relevant starting state` section of `requirements.md`: the facts about the project as it stands that the mission's decisions will rest on, gathered for its goal from the mission's scope first and then the adjacent material it reaches, from the record of earlier missions that bear on it, and from what the other live missions in overlapping scopes are deciding or doing. Run it after definition, before the first review. Run again later, it refreshes the section in place when the ground has moved since it was recorded (work landing in the scope, a hand commit there, or a revision of the mission's own goal), changing only what no longer holds and adding what is new, and it clears every standing recommendation on an open question that the changed facts undermine, keeping that question's alternatives. When nothing has moved since the last record, it explores nothing and says the starting state is current. You rarely need the re-run by hand: `/derive-tasks` and `/submit-task` refresh the section themselves when other missions' work has made it stale. Commits under `Starting-state: <path>`.

### `review-mission-requirements --mission <path>`

The repeatable engine of the requirements loop. Each pass reads `requirements.md`, the open questions, and an overview of the live and recently finished missions in overlapping scopes, then:

- **Reconciles** the open questions with what is decided: it removes a question a recorded decision covers, and an exact duplicate, and leaves in place a question it cannot point to a decision for. Removing a question clears the recommendation of every question whose pick depended on it.
- **Surfaces new gaps** as new open questions, each self-contained and asking one choice. Two choices that constrain each other are asked together. A recorded decision that rests on a starting-state fact that no longer holds is asked about again.
- **Turns contradictions into questions.** Each note under `## Noted contradictions`, which the single-question answer skills leave, and each pair of recorded decisions that cannot both hold becomes a question opening `Which conflicting decision stands: "<first heading>" or "<second heading>"?`. The pass never edits either entry or decides which one stands. Deleting the notes it has handled is its only edit of `requirements.md`.
- **Reports** the Short Titles still open, and, when none remain, the convergence line `Requirements converged — ready for task derivation.`

Run it after the starting state is recorded, then again after every answer or two, since answers open new questions; `/derive-tasks` runs only once no open question remains. It never answers a question. Commits under `Requirements-review: <path>`, and commits nothing on a pass that changed nothing.

### `discuss-open-question --mission <path> <Short Title>[. <note>]`

A conversation about one open question you cannot answer straight away, aiming at a concrete decision. Text after the first `.` followed by whitespace is an optional note, taken as your opening remark. It works on a question in any state: one that already carries alternatives reuses that set as it stands, and a bare one gets its alternatives enumerated first, in the same way the alternatives pass builds them. It then gives a recommendation of its own, shows the standing recommendation beside it when the question carries one and says whether the two agree, names any unanswered sibling question its pick leans on, and adds what would change its mind. When you decide, it offers `/answer-open-question`, naming the alternative's id when your answer is one of them; when the deliberation shows the goal itself must change, it offers `/modify-mission-goal`, to run first so the answer is recorded against the revised goal. It edits nothing.

### `answer-open-question --mission <path> <Short Title>. <answer text>`

Records your answer to one open question, word for word. The text is split at the first `.` followed by whitespace, so a Short Title naming a dotted file such as `CLAUDE.md wording` stays whole. The decision is written into `## Decisions` of `requirements.md` and the question is removed. Questions the decision makes moot are removed with it, and every other question's standing recommendation the answer undermines is cleared, keeping that question's alternatives for the next recommendation pass; when in doubt it clears. When the answer contradicts a recorded decision it plainly replaces, that entry is rewritten in place; when it only arguably does, the pair is noted under `## Noted contradictions` for the next review pass to ask about. An answer to a conflict question, one asking which of two decisions stands, rewrites the losing entry and adds nothing else. Commits under `Manual-answer: <Short Title>` with your rationale in the body, which `/capture-mission-principle-updates` later reads as an override of the recommender. The answer text `record the recommendation` is refused with a pointer to `/answer-open-question-with-recommendation`.

### `answer-open-question-with-recommendation --mission <path> <Short Title>`

Records one question's standing recommendation, the pick `/recommend-all-open-questions` embedded, as its answer, inline in the conversation so you can follow up. It records the same way `/answer-open-question` does: the decision written into `## Decisions`, the question removed, the questions it makes moot removed, an entry it plainly replaces rewritten and one it only arguably replaces noted, a conflict question answered by rewriting the losing entry. Questions whose own pick assumed a different outcome of this one have their recommendation cleared. A question carrying no recommendation stops the skill with nothing changed. Commits under `Recommendation-answer: <Short Title>`, which capture reads as an accepted recommendation: evidence for the principles already stored, never the source of a new one.

### `answer-open-question-with-alternative --mission <path> <Short Title>. <alternative id>`

Records the alternative you name, by its id, as one question's answer, inline in the conversation. Use it to override the recommendation or to settle a question the recommendation pass left tied. The text is split at the first `.` followed by whitespace; both halves match case-insensitively. It records the same way `/answer-open-question` does, and clears every other recommendation your choice undermines even when you choose the recommended alternative. A Short Title that matches no question, a question carrying no alternatives, or an id that matches none of them stops the skill with nothing changed. Commits under `Alternative-answer: <Short Title>`; since the body carries only the alternative's text, `/capture-mission-principle-updates` later asks you why you preferred it. There is no batch form: which alternative wins is your judgment, question by question.

### `answer-all-open-questions-with-recommendation --mission <path>`

The answer sweep: records the standing recommendation of every question carrying one, unattended, without judging any pick. It takes the questions in dependency order, so a pick is recorded only after the sibling picks it assumed, and commits each answer on its own under `Recommendation-answer: <Short Title>`, so a single answer can be reverted and re-answered. A question whose pick an earlier answer in the run cleared is skipped, for the next recommendation pass to re-pick; a question without a recommendation is left as it is. An answer to a conflict question rewrites the losing entry. The sweep removes no moot question and notes no contradiction, leaving both to the next review pass. It stops before writing anything when `requirements.md` or `open_questions.xml` already holds uncommitted changes, and stops at the first answer it cannot record, keeping every earlier answer committed and the rest of the tree as it stands; commit or discard the leftover changes before re-running. Run it after `/recommend-all-open-questions`.

### `modify-mission-goal --mission <path> <new or revised goal text>`

Revises the `## Goal` of a mission already defined, the one skill that changes a live mission's goal. The text may be a whole new goal or a change to fold into the current one. In the same commit it clears every standing recommendation the revised goal undermines, keeping those questions' alternatives, so the answer sweep cannot record a pick formed under the old goal. Clearing those picks is all it does beyond the goal: it removes, adds, or rewords no question, decision, out-of-scope entry, or task, and leaves the rest of the impact for you to reconcile with `/review-mission-requirements`. `/discuss-open-question` offers it when a deliberation shows the goal must change. Commits under `Goal-revision: <path>`.

### `capture-mission-principle-updates <path>`

Distils reusable answering principles from one mission's recorded answers into the project's principle store, `answer_decision_principles.md` at the project root, which the recommendation pass reads as advice. It takes the mission's path as a plain argument, not `--mission`, because the mission may already be finished: it works on a live mission or a finished one whose `requirements.md` the history still holds. Run it whenever you like, right after `/finish-mission` being the natural moment; finishing never runs it. Your manual and alternative answers that overrode a recommendation are what teach it new principles, and it asks you for the reason behind each one that records none, offering its own guess; accepted recommendations only reinforce or flag the principles already stored. It writes the whole revised store in place for you to read with `git diff`, takes your change requests in conversation, and commits under `Principle-capture: <path>` only once you confirm; if you decline, it restores the store as it was. A mission captured before, or a store with uncommitted edits, gets one notice and one question whether to go on.

### `provide-alternatives-to-all-open-questions --mission <path>`

The alternatives pass, the first of the two annotating passes. For every open question that carries no alternatives yet, it dispatches one `provide-alternatives-to-open-question` subagent, together rather than one after another where the host allows, and embeds each returned set of alternatives into the question, committing each under `Alternatives-annotation: <Short Title>`. A set is built to be distinct and covering: every two options differ in substance, and together they cover the decision itself, not doing the thing included where that is viable. A set the open-question tool refuses gets one repair; a question still left without alternatives is listed in the report, and a re-run retries exactly those. A question that already carries alternatives is never touched, so the set the recommendation pass picks from stays frozen; to replace one, clear it with the open-question tool's `strip` and re-run. It needs no clean working tree.

### `provide-alternatives-to-open-question` (subagent)

Dispatched once per question by `/provide-alternatives-to-all-open-questions`; you never run it yourself. It reads its own question, the text of the sibling questions as scope, `requirements.md`, and the project, and enumerates the honest alternatives: it names the axes the decision turns on, builds each option as one position on them, and states for each what it is, its advantage, and its drawback. It changes nothing in the project; its one write is its return, a file outside the repository that the pass embeds and commits.

### `recommend-all-open-questions --mission <path>`

The recommendation pass, the second annotating pass. Over every question that has alternatives and no recommendation yet, it picks one alternative per question, weighing the whole set at once in the conversation so the picks agree with one another and with the recommendations already standing; it weighs the project, the principle store, and the sibling questions. Each pick carries a one-line rationale, the principles that bore on it, and the sibling outcomes it assumed. A set a recorded decision has partly outdated still gets its best surviving option, and a question none of whose options survives is skipped and listed. It stops before picking anything while any question still lacks alternatives. It commits the picks together under `Recommendation-annotation: <path>`, then puts the questions into the order the answer sweep will record them and, when that moved a question, commits the new order under `Question-ordering: <path>`. A standing recommendation is never picked again; to have one re-picked, clear it with the open-question tool's `strip --recommendation` and re-run. It needs no clean working tree.

### `derive-tasks --mission <path>`

Turns a converged mission's `requirements.md` into `TASKS_TODO.md`: a complete, dependency-ordered list of brief-level tasks, each a title and one to three sentences on what is to be achieved, why, and how it would be verified. It proves that every requirement maps to a task, skipping what a completed task already satisfies, presents the plan, which you may interrupt to adjust, and writes the whole list in one commit under `Task-derivation: <path>`, replacing what the file held. It requires that no open question remains. Where two recorded decisions cannot both hold, the one recorded later, by its commit, governs the tasks; a standing contradiction note does not block it. It checks the scope gate at the start and again just before it writes: while another started mission (one whose tasks were ever entered and whose directory still stands) has its scope in the same directory, one enclosing it, or one beneath it, the run stops with that mission's path listed, and defining and preparing a mission never waits on that gate. When other missions' work has landed in the scope since the starting state was recorded, it refreshes the starting state first, as its own `Starting-state:` commit.

### `discuss-new-task --mission <path> <issue description>`

A short conversation that turns a rough issue found mid-flight into one or more task-sized descriptions, each clear on which part of the project it touches, what should be true afterwards, and how to check it. It first checks whether a pending or completed task already covers the issue. When the issue is several tasks, it proposes an ordered split for your sign-off. On your confirmation it hands each description to `/submit-task`, in dependency order. Use it when the system, the desired behaviour, or the check is not yet clear, or when one issue is really several. It edits nothing itself.

### `submit-task --mission <path> <issue description>`

Adds one already-clear issue to `TASKS_TODO.md` as a brief-level task, in the same shape `/derive-tasks` writes, inline in the conversation so you can adjust it afterwards. It refuses a duplicate of a pending or completed task and an issue that belongs to another mission or is really an open decision, pointing at the better tool. It places the task before a task that needs it, after one it needs, or at the end. Like `/derive-tasks`, it checks the scope gate before it starts and again just before it inserts, and it refreshes a starting state that other missions' work has made stale. An issue too vague to write as a task stops it. Commits under `Task-submission: <task title>`. For a vague or multi-task issue, run `/discuss-new-task` first.

### `complete-all-tasks --mission <path>`

Completes the whole task list unattended, top to bottom, one fresh subagent per task. Each subagent derives the task's acceptance bar from its brief and the mission's decisions, does the work, verifies it against that bar, and removes the task from the list. The run commits each task on its own under `Task-completion: <task heading>`, with the verified bar as the commit body; that commit is the completed task's whole record. Before changing an existing file that the mission does not explain, a subagent may read the completed tasks that changed it and the decisions behind them, so it does not undo by accident what an earlier mission chose on purpose. The scope gate is checked before every task. The run stops at the first task that fails or cannot be committed, keeping every earlier task committed and leaving the failed task's partial work uncommitted, for a later run to resume.

### `complete-task --mission <path> <task name>`

Completes one named task inline, in the conversation, so you can ask about the work or request tweaks right after. The name may be any part of a task's heading; a name matching none stops the skill with the headings listed. It works exactly as a `/complete-all-tasks` subagent does, scope gate included, and commits the same `Task-completion: <task heading>` commit with the verified bar as its body.

### `ask-in-mission-context --mission <path> <question>`

Answers an informational question about the mission from its goal, decisions, pending and completed tasks, and what those tasks actually produced, and, when the question reaches into past work, from the project's record of its missions, finished ones included. With no question it gives a short orientation. Use it to look back on finished work, to take stock of what is left and why, or to gather context before deciding what to do next. When the answer points at a next step it names the skill for it, but does none of that skill's work. It edits nothing.

### `finish-mission --mission <path>`

Finishes a mission once no open question and no task remains, and stops with what is still open otherwise. It composes a summary of three to eight bullets from the goal, the completed tasks, and the decisions, updates the context file only for lasting changes to how the project is worked on, and removes the mission's directory in one `Mission-finish: <path>` commit whose body is the mission's title and that summary. A mission is finished exactly when its directory is gone: its files stand in the commit before the finish, the summary is read back from the finish commit, and reverting that commit makes the mission live again. It does not run `/capture-mission-principle-updates`.

## Fixed console lines

Every skill's report opens with one fixed line saying how the run ended, carrying no mission path, title, or count: its **success** line when it did its work, a **no-op** line when it ended cleanly having changed nothing, or a **stop** line when it stopped short. Whatever detail a stop needs, such as a tool's `Error:` line, the open questions it found, or the remedy, follows on the lines below it. No skill sets an exit code, so when you chain skills as headless command lines this first line is how a harness tells a clean end from a stop, and which stop it was. One listed line is not a first line: the **verdict** line `/review-mission-requirements` prints below its list of open questions whenever none remains, which a harness looping review and answer passes matches to leave the loop. The conversational `discuss-mission-goal`, `discuss-new-task`, and `ask-in-mission-context` print no fixed line. Every line is listed, exactly as printed, in [`tests/fixed_console_lines.tsv`](../tests/fixed_console_lines.tsv), one row per line with the skill or shared step that prints it, its kind, and the line; a line printed by several skills, such as a mission path that matches no mission, is listed once.
